Scope: `dracon-sync/src/git/` — mod.rs, multi_remote.rs, status.rs, staging.rs,
branch.rs, ops.rs, push.rs, diff.rs, discovery.rs, config.rs, urls.rs, misc.rs.
Research-only; no source files modified.

Lens applied: raw-field-vs-accessor, multi-placeholder replace, uncached network

## Verified clean (checked, no finding)

- **`is_stable_empty_repo` worktree case**: correctly refuses `.git`-file

- **`rewrite_ahead_paths` gating**: the only call site is report.rs:4900 under

- **discovery symlink escape**: `discover_git_repos_recursive` skips

- **`-z` usage**: `git_diff_head_files`, `untracked_entries`, `staged_paths`,
  `tracked_paths` all use `-z` (but see F2.8 for the two that don't).

## Findings

### F2.1 — [SEVERITY: MEDIUM] `repair_broken_tracking` never repairs the checked-out branch
- **Location**: branch.rs:300-312
- **What**: Branch-name extraction takes the first whitespace token of the
  `git branch -vv` line. For the *current* branch the line is
  `* main abc1234 [origin/main: gone]`, so the first token is `"*"`,
  `trim_start_matches('*')` yields `""`, and the `branch.is_empty()` guard
  skips it. Only *non-checked-out* branches are ever repaired.
- **Evidence**:
  ```rust
  let branch = trimmed
      .split_whitespace()
      .next()                       // "*" for the current branch
      .map(|s| s.trim_start_matches('*'))
      .unwrap_or("")                // → "" → skipped by is_empty() guard
  ```
  The test `test_old_tracking_from_status_line_parses_real_ref` feeds exactly
  such a `* main ...` line to the *parser* but the branch-extraction bug is
  upstream of the parser and untested.
- **Impact**: The one branch that matters (the one the daemon pushes) keeps a
  `gone` upstream forever; startup repair (daemon.rs:1900, 2359) logs nothing
  and the broken-tracking state persists across restarts.
- **Suggested fix**: If the line starts with `*`, take the *second* token as
  the branch name; otherwise the first. Add a regression test with a
  `* main ... [origin/main: gone]` line asserting `main` is repaired.

### F2.2 — [SEVERITY: MEDIUM] `rewrite_ahead_paths` filter-branch fallback builds a broken argv
- **Location**: staging.rs:210-228
- **What**: When `git filter-repo` is absent, the fallback appends
  `paths_to_remove` as *positional argv entries after* the `--index-filter`
  string and before `--`:
  ```rust
  let filter_expr = "git rm -r --cached --ignore-unmatch".to_string();
  args.push(filter_expr);                        // the shell command — NO paths
  args.extend(paths_to_remove.iter().cloned());  // treated as rev-list args
  args.push("--".to_string());
  ```
  Two independent breakages: (1) `git rm -r --cached --ignore-unmatch` with no
  pathspec dies with "fatal: No pathspec was given", so the index-filter fails
  on every commit; (2) filter-branch forwards the trailing positionals to
  `git rev-list`, where a path like `assets/big.mp4` is parsed as a *revision*
  and dies with "bad revision". The fallback can never succeed.
- **Impact**: On any host without git-filter-repo, the large-blob auto-repair
  always errors out (after creating the backup branch), so the pack-too-large
  concern is never remediated. Latent — production hosts currently have
  filter-repo, which is why this hasn't fired.
- **Suggested fix**: Build the filter as a single quoted shell string
  (`format!("git rm -r --cached --ignore-unmatch -- {}", shell_quoted_paths)`),
  then `--`, then an explicit rev range. Note also (doc drift): the filter-repo
  arm rewrites *all* refs, not just commits "ahead of the remote" as AGENTS.md
  phrases it — harmless for the intended use but worth a comment.

### F2.3 — [SEVERITY: MEDIUM] `is_safe_git_path` only inspects the first two components for `..`
- **Location**: discovery.rs:573-589
- **What**: The traversal check calls `components.next()` twice and rejects
  `..` only in position 1 or 2. `a/b/../../etc` (components `a, b, .., ..`)
  passes the check, as does any path whose `..` appears at depth ≥ 3.
- **Evidence**:
  ```rust
  let mut components = path.components();
  if let Some(first) = components.next() { if first.as_os_str() == ".." { return false; } }
  if let Some(first) = components.next() { if first.as_os_str() == ".." { return false; } }
  ```
- **Impact**: This is the F32 guard for `restore_paths` and the gate for
  `unstage_*`/`is_nested_repo_path`. Inputs today come from `git` itself
  (which never emits `..`), so this is defense-in-depth rather than a live
  hole — but the guard does not deliver what its name and the F32 comment
  promise. If any future caller passes operator- or file-derived paths, a
  deep `..` sails through to `git restore --staged --worktree -- <path>`.
- **Suggested fix**: Reject if `path.components().any(|c| matches!(c,
  Component::ParentDir))` (and keep the absolute/`-` checks).

### F2.4 — [SEVERITY: MEDIUM] `.status()` exit codes ignored at many call sites
- **Location**: multi_remote.rs:28-38 (`ensure_remote`), multi_remote.rs:199
  (`branch.<name>.remote` config), branch.rs:121-126 (`checkout main`),
  branch.rs:150-154 (`branch -m master main`), misc.rs:74-80
  (`fix_orphan_origin`), staging.rs:37/70 (`git reset` unstage chunks)
- **What**: The recurring pattern
  `cmd.status().with_context(...)?` (or `.status().await?`) only surfaces
  *spawn* failure. A non-zero exit from the git process is silently treated
  as success.
- **Evidence**: `consolidate_to_main` proceeds to `branch -D master` and
  `push origin --delete master` even when `git checkout main` failed (e.g.
  dirty working tree blocking the checkout) — the delete then runs on the
  wrong branch context. In `unstage_excluded_paths`/`unstage_oversized_paths`
  the count returned to the caller claims paths were unstaged even if
  `git reset` exited non-zero.
- **Impact**: Silent no-ops reported as success; in the consolidate case, a
  destructive follow-up (branch deletion) executes on a failed precondition.
- **Suggested fix**: Check `.success()` on every `ExitStatus` and bail with
  stderr context (same shape as `child_status_result` in ops.rs). A small
  `status_checked(cmd) -> Result<()>` helper would kill the whole class.

### F2.5 — [SEVERITY: MEDIUM] `remote_repo_exists`: uncached per-push network call; any error looks like "missing"
- **Location**: multi_remote.rs:614-629, called from
  `auto_create_all_remotes` (multi_remote.rs:584-594)
- **What**: Every push cycle runs `auto_create_all_remotes`, which — for each
  remote with effective `auto_create = true` — shells out
  `git ls-remote <name> HEAD` over SSH. No caching, no negative-result TTL.
  Any failure (network down, DNS, ssh key change, remote-side 5xx) returns
  `false`, indistinguishable from "repo does not exist", which then triggers
  `gh repo create` / `glab repo create` / Codeberg REST create.
- **Impact**: (a) Adds one SSH round-trip per auto-create remote per push —
  measurable latency on the push path, and GitHub rate-limit exposure on the
  create side. (b) During a network partition the daemon fires spurious
  create attempts every cycle; the `already exists` handlers (gh/glab/409)
  currently mask the misclassification, so this is latent rather than live.
- **Suggested fix**: Cache "exists" per (repo, remote) for the daemon's
  lifetime after the first success (a repo, once created/existing, is almost
  never deleted), and treat transport errors as `unknown` → skip create this
  cycle rather than `false` → create.

### F2.6 — [SEVERITY: MEDIUM] "Repository not found" / "Push to create is not enabled" are not classified as permanent push failures
- **Location**: push.rs:241-263 (`is_permanent_push_rejection`,
  `is_pack_too_large`); retry loop in multi_remote.rs:430-470
- **What**: The permanent-rejection classifier covers protected branches and
  hook declines, and the pack-size classifier covers GH001-style errors.
  Nothing matches a *deleted/missing remote repo*:
  `remote: Repository not found.`, `Forgejo: Push to create is not enabled`,
  `The project you were looking for could not be found`, or
  `Permission denied (publickey)`.
- **Impact**: If a forge repo is deleted (or the key rotated) while
  `auto_create` is off for that remote — exactly the v0.112.28 codeberg
  posture — every push burns the full retry budget (with backoff sleeps) on
  every cycle, forever, and the repo marches toward PUSH_STUCK even though
  the condition is definitionally unfixable by retrying. The v0.112.30
  codeberg exclusion handles *new* repos, but a pre-existing repo whose
  codeberg mirror is deleted (tracking ref still present locally) loops
  forever.
- **Suggested fix**: Add these substrings to `is_permanent_push_rejection`
  (or a dedicated `is_remote_repo_gone` class) so the failure is logged once
  per cycle without retries; ideally surface a distinct CONCERN ("remote
  repo missing — recreate or exclude").

### F2.7 — [SEVERITY: MEDIUM] `IndexLock` can never be acquired for `.git`-file worktrees/submodules — standard files silently skipped every cycle
- **Location**: status.rs:29-45 (`IndexLock::acquire`), sole caller
  sync.rs:3415-3428
- **What**: The lock path is hardcoded as `repo.join(".git").join("index.lock")`.
  For a linked worktree or a submodule (the nested-on-`main` game repos —
  the canonical architecture since 2026-07-02), `<repo>/.git` is a *file*,
  so creating `<repo>/.git/index.lock` fails with ENOTDIR. `acquire` returns
  `Err("failed to create index.lock ... Not a directory")`, the caller logs
  it (debug-only) as if another git op held the lock, and
  `ensure_standard_files` is skipped — **every cycle, forever**, for every
  submodule/worktree repo.
- **Impact**: Nested game submodules never receive standard files
  (`.gitattributes` etc.) from the daemon; the debug log message actively
  misleads (claims lock contention, actually a wrong path). No data loss.
- **Suggested fix**: Resolve the real gitdir first (the crate already has
  `resolve_head_path`/`path_gitdir` logic that parses the `gitdir:` pointer)
  and create `index.lock` there — for a submodule that is
  `<parent>/.git/modules/<name>/index.lock`, matching where git itself takes
  the lock.

### F2.8 — [SEVERITY: MEDIUM] `cli_diff_entries` / `git_name_status_entries` parse `--name-status` without `-z`; failure indistinguishable from "no changes"
- **Location**: diff.rs:100-119, 133-147
- **What**: Two problems. (1) No `-z`: with default `core.quotePath=true`,
  git C-quotes paths containing bytes ≥ 0x80 or special chars — a file
  `café.rs` arrives as `"caf\303\251.rs"` (quotes included) and
  `parse_name_status_line` turns that literal into a `PathBuf` that matches
  nothing on disk. Newline-in-filename breaks line-based parsing outright.
  The sibling functions in the same file (`staged_paths`,
  `untracked_entries`, `git_diff_head_files`) all use `-z`, so the
  inconsistency looks accidental. (2) `git_name_status_entries` returns
  `Ok(Vec::new())` on non-zero exit — a failed `git diff` is reported to the
  caller as "zero changed files", and `cli_diff_entries` doesn't check the
  exit status at all.
- **Impact**: Repos containing non-ASCII filenames have those files' diffs
  silently dropped from `repo_diff_entries` — the daemon can under-report or
  mis-stage changes for exactly the files most likely to need attention.
  Swallowed diff failures read as "clean".
- **Suggested fix**: Add `-z` (and `-c core.quotePath=false` is then
  unnecessary) to both commands and split on `\0`; check the exit status and
  propagate an `Err` instead of `Ok(vec![])`.

### F2.9 — [SEVERITY: MEDIUM] `remove_stale_remotes` deletes operator-added remotes
- **Location**: multi_remote.rs:330-348; invoked on every push via
  `push_mirror_remotes` (multi_remote.rs:263-268) and on the create-only path
- **What**: Any remote that is not literally `origin` and not in the policy
  keep-list is `git remote remove`d. An operator who adds a personal remote
  (`backup`, `mirror-to-nas`, a fork) to a daemon-watched repo loses it on
  the next push cycle, along with that remote's tracking refs.
- **Impact**: Silent destruction of operator git config. Recoverable
  (re-add), but surprising and undocumented in AGENTS.md's operator-facing
  sections. Note the v0.112.30 codeberg-exclusion path now uses this to
  *intentionally* strip the codeberg remote, so the function is load-bearing
  — the fix is scoping, not removal.
- **Suggested fix**: Only remove remotes the daemon itself manages (e.g.
  names present in the policy remotes list historically, or a
  `dracon.managed=true` config marker stamped at `ensure_remote` time), or
  gate the behavior behind a policy flag defaulting to off for unknown
  names.

### F2.10 — [SEVERITY: LOW] First SSH push in `push_to_named_remote` uses the branch name without `is_safe_branch_name`
- **Location**: multi_remote.rs:356-374 vs 399-410
- **What**: The first attempt builds `HEAD:refs/heads/{branch}` and pushes it
  unconditionally; the `is_safe_branch_name(&branch)` gate only wraps the
  HTTPS fallback. The retry loop then switches to bare `HEAD` (multi_remote.rs:414)
  — which also reintroduces the detached-HEAD "not a full refname" failure the
  refspec form was added to fix (goal `354fe3cb`), so on a detached worktree
  attempt 1 has a chance but every retry is guaranteed to fail differently.
  Separately, `is_safe_branch_name` itself (discovery.rs:592-617) misses some
  git-forbidden constructs: `@{`, leading `/`, trailing `/`, `.lock` suffix,
  and control chars like `\t`.
- **Impact**: Low — all values are argv-passed (no shell), and HEAD content is
  git-controlled in practice. Worst case is a malformed refspec error. The
  detached-HEAD retry inconsistency is the more real half of this finding.
- **Suggested fix**: Validate once at the top, reuse the same explicit
  refspec in the retry loop, and extend `is_safe_branch_name` (or delegate to
  `git check-ref-format --branch`).

### F2.11 — [SEVERITY: LOW] `kill_process_group`: 2 s blocking sleep in async context; no SIGKILL when `kill` is missing
- **Location**: ops.rs:27-50, called from ops.rs:184-196
- **What**: `std::thread::sleep(Duration::from_secs(2))` runs on a tokio
  worker thread inside the async timeout path (runtime is
  `multi_thread`, main.rs:484 — one stalled worker per concurrent kill,
  not fatal). Also, if the SIGTERM shell-out itself fails (no `kill` on
  PATH, ESRCH race), the function returns *without* attempting SIGKILL;
  only the direct child is killed by the caller's `start_kill()`, so
  grandchildren (ssh, remote-https) can survive and linger.
- **Impact**: With N remotes timing out simultaneously (network partition),
  N workers stall for 2 s each; orphaned ssh helpers may outlive the push.
- **Suggested fix**: `tokio::time::sleep` for the grace window (or a small
  `spawn_blocking`), and always attempt the SIGKILL shell-out regardless of
  the TERM result — KILL on a dead pgid is harmless.

### F2.12 — [SEVERITY: LOW] `push_to_all_remotes`: stale SEQUENTIAL doc comment over parallel implementation; join errors lose the remote name
- **Location**: multi_remote.rs:472-537
- **What**: The doc comment still describes the goal `87c1bf4d` sequential
  design and the race it eliminated, followed by a "CHANGED 2026-06-20:
  sequential → parallel" note using `tokio::spawn`. The implementation
  *does* await all futures before returning, so the cross-cycle race the
  comment warns about is not reintroduced — but the comment block
  contradicting itself invites a future "fix" of a non-bug. Also, a join
  error is reported under the literal name `"unknown"`, losing which remote
  panicked.
- **Impact**: Cosmetic/operational clarity only.
- **Suggested fix**: Rewrite the doc comment to state the current invariant
  ("parallel within a cycle, fully drained before the next cycle"), and zip
  the futures with their remote names so a JoinError names the remote.

### F2.13 — [SEVERITY: LOW] `detect_large_blobs_ahead`: paths with spaces truncated; missing upstream silently yields "no large blobs"
- **Location**: staging.rs:76-144
- **What**: (1) `cat-file --batch-check` output is parsed with
  `split_whitespace()` and `parts.next()` for the path — `%(rest)` of
  `assets/my video.mp4` truncates to `assets/my`, so the subsequent
  `filter-repo --path assets/my` is a no-op rewrite (cleaned up by F31, so
  the large blob simply survives undetected-as-fixed). (2) The rev-list uses
  `@{u}..HEAD`; on a repo with no upstream configured this fails and the
  function returns `Ok(Vec::new())` — "no upstream" is conflated with "no
  large blobs ahead".
- **Impact**: The large-blob auto-repair can silently miss exactly the files
  (space-named media) most likely to trip GitHub's limits; mirror-only repos
  without upstreams are never scanned.
- **Suggested fix**: Parse with `splitn(4, ' ')` and take the remainder as
  the path; fall back to `HEAD` (or the mirror tracking refs) when `@{u}`
  doesn't resolve.

### F2.14 — [SEVERITY: LOW] Discovery still generates watch-root standalone candidates when the nested submodule path is missing (SUSPECTED)
- **Location**: discovery.rs:131-153
- **What**: For each `.gitmodules` entry whose nested path is absent, the
  "legacy fallback" pushes `<watch_root>/<basename>` (e.g. `/Dev/polis`) into
  the repo list even though that directory does not exist on disk. This
  predates the 2026-07-08 removal of standalone materialization (goal
  `730eaf2a`): nothing will ever create that directory now, so the daemon
  carries ghost repo entries every cycle.
- **Impact**: SUSPECTED — downstream consumers may filter nonexistent paths
  (not verified; sync/report handling is outside this audit's scope). If they
  don't, every cycle logs errors for phantom repos and the `repos` table
  shows dead rows.
- **Suggested fix**: Drop the standalone fallback (or skip candidates whose
  path doesn't exist and has no `.git`), matching the post-730eaf2a
  architecture.

### F2.15 — [SEVERITY: LOW] Stale `index.lock` bricks a repo if the daemon dies while holding `IndexLock`
- **Location**: status.rs:29-57
- **What**: `IndexLock` creates `.git/index.lock` via `O_EXCL` and unlinks it
  in `Drop`. A SIGKILL (OOM, systemd `TimeoutStopSec` hard kill) between
  acquire and drop leaves the lock file behind; git itself never removes
  stale `index.lock` files, so *every* subsequent git index operation in that
  repo — including the daemon's own staging — fails with
  "Unable to create ... index.lock: File exists" until a human deletes it.
- **Impact**: One repo wedges permanently (for writes) after an unlucky kill;
  the daemon's error would surface as staging failures, not as "stale lock".
- **Suggested fix**: On `acquire` hitting `AlreadyExists`, stat the lock:
  if older than a threshold (e.g. 10 min), log loudly and remove it (git's
  own staleness heuristic is "never", but for a single-writer daemon a TTL
  is defensible); at minimum surface a distinct CONCERN instead of a generic
  skip.

### F2.16 — [SEVERITY: LOW] Minor parser/hardcoding nits
- **`parse_name_status_line` trims paths** (diff.rs:84): `path.trim()`
  corrupts legal filenames with leading/trailing spaces. With `-z` (F2.8)
  the trim should simply be deleted.
- **`count_unpushed_vs_mirrors` hardcodes `main`** (status.rs:281-286): the
  mirror refs `refs/remotes/{github,gitlab,codeberg}/main` miss repos whose
  primary branch is `master` (pre-consolidation) — the v0.112.30
  ahead-override then under-counts until `count_all_head_commits` catches it
  (only when `upstream_ref_missing`).
- **`has_codeberg_tracking_ref` `.unwrap_or(false)`** (multi_remote.rs:81-90):
  a transient `git rev-parse` failure reads as "never pushed" → codeberg
  excluded → `remove_stale_remotes` strips the codeberg remote that cycle.
  Self-healing next cycle, but the remote flap churns `.git/config`.
- **`detect_orphan_origin` suffix heuristic** (misc.rs:45-66): any repo whose
  name ends in `-<digit>` (e.g. `webgpu-2`) is classified as an orphan
  `-N` repo regardless of whether the canonical repo exists.

## Summary

1. Two genuinely broken code paths found: `repair_broken_tracking` skips the
   checked-out branch (F2.1) and the `filter-branch` fallback in
   `rewrite_ahead_paths` can never succeed (F2.2) — both latent, both
   untested at the failure point.
2. The `.auth_type` raw-field class is fully remediated in src/git; the new
   systemic weakness is the inverse class — `.status()` exit codes ignored
   at ~6 call sites (F2.4), including a destructive `consolidate_to_main`
   sequence that proceeds on a failed `checkout`.
3. Error classification remains the biggest loop-risk: deleted remote repos
   ("Repository not found" / "Push to create is not enabled") retry forever
   under the v0.112.28 auto-create-off posture (F2.6), and
   `remote_repo_exists` conflates network failure with repo-missing on every
   push, uncached (F2.5).
4. Worktree/submodule handling is half-done: `IndexLock` silently skips
   standard-file writes for every nested-on-main submodule (F2.7), while
   `is_safe_git_path`'s two-component `..` check (F2.3) and the non-`-z`
   diff parsers (F2.8) leave guard/parsing gaps the sibling code already
   solved.
5. Totals: 0 HIGH, 9 MEDIUM, 7 LOW (one SUSPECTED: F2.14). No secrets
   exposure, no shell-injection vector, and the history-rewrite gate +
   backup-branch discipline verified intact.

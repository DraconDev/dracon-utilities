# Audit Part 3: policy/ownership/visibility/secrets/report/main (2026-07-21)

Scope: src/policy.rs, ownership.rs, visibility.rs, secrets.rs, exclude.rs,
report.rs, main.rs, role.rs, bump.rs. Research only; no source modified.

## Findings

### F3.1 — [SEVERITY: HIGH] CODEBERG_API_REPOS still has the two-placeholder `str::replace` bug (the GitLab bug's twin)
- **Location**: src/visibility.rs:260 (constant), :328 (`set_codeberg_visibility`), :770 (`set_codeberg_metadata`)
- **What**: The v0.112.29 GitLab fix (`GITLAB_API_PROJECTS` reduced to a single `{}`) was NOT applied to the Codeberg template. `CODEBERG_API_REPOS = "https://codeberg.org/api/v1/repos/{}/{}"` has TWO `{}` placeholders, and both call sites do:
  ```rust
  let url = CODEBERG_API_REPOS.replace("{}", &format!("{}/{}", owner, repo));
  ```
  `str::replace` substitutes ALL occurrences → the produced URL is
  `https://codeberg.org/api/v1/repos/dracondev/web-games-x/dracondev/web-games-x`.
  The Gitea route `/api/v1/repos/{owner}/{repo}` does not match a 4-segment path → 404 on every call. The fix comment at visibility.rs:250-258 even says "Same pattern as the codeberg template below" — the author looked at the codeberg template and believed it was fine because it "legitimately" has two slots, missing that the replace passes the combined `owner/repo` to BOTH slots.
- **Evidence**: `const CODEBERG_API_REPOS: &str = "https://codeberg.org/api/v1/repos/{}/{}";` vs `GITLAB_API_PROJECTS` (single `{}` after fix). The regression-pinning test `test_gitlab_api_url_construction` (visibility.rs:1176-1192) has no Codeberg equivalent — `test_set_codeberg_visibility_builds_correct_request` (:1195) only checks the function doesn't panic.
- **Impact**: Every Codeberg visibility flip (`make-public/make-private --include-codeberg`) fails with "repo not found" (exit 2 partial failure), and every daemon-side `sync_mirror_visibility`/`sync_mirror_metadata` Codeberg call 404s (eprintln only, non-fatal). Codeberg visibility sync is silently broken for all repos.
- **Suggested fix**: Replace the two slots with named or sequential substitution — either `CODEBERG_API_REPOS.replace("{owner}", owner).replace("{repo}", repo)` with a `{owner}/{repo}` template, or `format!("https://codeberg.org/api/v1/repos/{}/{}", owner, repo)` directly. Add a URL-pinning test mirroring `test_gitlab_api_url_construction`.

### F3.2 — [SEVERITY: MEDIUM] TOML field-ordering check suppresses exactly the case that matters; live production config has a silently-ignored field TODAY
- **Location**: src/policy.rs:1579-1637 (`check_toml_field_ordering`), policy.rs:362 (`SyncPolicy` — no `deny_unknown_fields`), policy.rs:135 (`RemoteConfig` — no `deny_unknown_fields`)
- **What**: The check sets `in_table = true` on `[[...]]` and then warns ONLY when `!in_table`. But TOML absorbs trailing bare keys into the LAST `[[table]]` entry — so a misplaced top-level field after any `[[remotes]]`/`[[standard_files]]` block is (a) silently ignored by serde (no `deny_unknown_fields` on RemoteConfig/StandardFileConfig) and (b) NOT warned about by the checker. Verified against the live config with `tomllib`:
  ```
  /home/dracon/.dracon/utilities/sync/dracon-sync.toml:277
  standard_files_auto = true   # placed after two [[standard_files]] blocks
  → parses as standard_files[-1]['standard_files_auto'], NOT top-level
  → top-level 'standard_files_auto' in d == False
  ```
  The operator's explicit setting is silently ignored (currently harmless: default is also `true`). The `[extra_remotes]` section (line 285) likewise maps to no SyncPolicy field and is silently dropped.
- **Evidence**: `python3 tomllib` parse of the live config (run during this audit): `last standard_files entry: {'source': 'templates/FUNDING.yml', ..., 'standard_files_auto': True}`.
- **Impact**: The documented footgun is live in the operator's own config; the detection mechanism has a blind spot exactly where the footgun lives. Any future top-level field appended at the bottom of the file vanishes with zero diagnostics.
- **Suggested fix**: In `check_toml_field_ordering`, keep a set of known per-table keys (RemoteConfig/StandardFileConfig field names) and warn when a post-`[[table]]` bare key is NOT in that set (or IS a known SyncPolicy key). Long-term: add `#[serde(deny_unknown_fields)]` to RemoteConfig and StandardFileConfig (SyncPolicy itself must stay permissive or gain an explicit unknown-key linter, since `[extra_remotes]`-style legacy sections exist).

### F3.3 — [SEVERITY: MEDIUM] `config validate` hides all warnings when there are no errors
- **Location**: src/main.rs:739-755
- **What**: `if result.is_valid() { println!("✅ Policy is valid"); } else { ...print errors AND warnings... }`. On the success path, `result.warnings` is never printed — including the TOML-ordering warnings (F3.2), low-timeout warnings, and missing-token-file warnings.
- **Evidence**: read of main.rs Config::Validate arm; contrast with `health` (main.rs:1176-1182) which does print warnings.
- **Impact**: The only command whose entire job is config linting reports "✅ Policy is valid" while withholding every warning it collected. Operators never see the footgun warnings unless they run `health`.
- **Suggested fix**: Print warnings unconditionally after the validity verdict (and consider exit code 0 with warnings, 1 with errors — current behavior already exits 1 only on errors).

### F3.4 — [SEVERITY: MEDIUM] `expand_tilde("~/x")` resolves to `/x` (filesystem root), not `$HOME/x`
- **Location**: src/policy.rs:90-98
- **What**: `path.strip_prefix('~')` on `"~/templates/LICENSE"` yields `"/templates/LICENSE"` (leading slash retained); `home.join("/templates/LICENSE")` REPLACES the base because the argument is absolute (documented `Path::join` behavior). Verified by compiling the exact function: `expand_tilde("~/templates/LICENSE") == "/templates/LICENSE"`. The `~foo` form (no slash) maps to `$HOME/foo` — also wrong (`~foo` means foo's home).
- **Evidence**: `rustc` reproduction during audit: output `"/templates/LICENSE"`, `"/home/dracon/templates/LICENSE"` (for `~templates/...`), `"templates/LICENSE"`.
- **Impact**: Any `standard_files[].source = "~/..."` silently resolves to a root-relative path that doesn't exist → "template missing" skip (standard_files.rs:39-45). The F40 validation (:1470-1490) only rejects literally-absolute sources, so the broken form passes validation. Currently dormant (live config uses relative `templates/...`).
- **Suggested fix**: Strip the optional `/` after `~`: `let rest = rest.strip_prefix('/').unwrap_or(rest);` before `home.join(rest)`, and add a unit test for `~/x`, `~x`, and bare `~`.

### F3.5 — [SEVERITY: MEDIUM] `make-public`/`make-private` writes the visibility cache on ANY remote success, even when the GitHub leg failed
- **Location**: src/main.rs:462-470 (`handle_visibility_flip`)
- **What**: `let any_success = results.iter().any(|(_, r)| r.is_ok()); if any_success { update_visibility_cache(&repo_path, target_private); }`. The cache is the codeberg-gate's source of truth for GITHUB visibility (sync.rs:1509, report.rs:568). If the GitHub flip fails (e.g. `gh` auth hiccup) but the GitLab flip succeeds, the cache records the TARGET state even though GitHub never flipped.
- **Impact**: `make-public` with a failed GitHub leg poisons the cache to "public" → the `codeberg_public_only` gate starts pushing the repo to Codeberg (world-visible forge) while the canonical GitHub repo is still private. Reverse direction: `make-private` with failed GitHub leg caches "private" → codeberg pushes silently stop. Exit code 2 is returned, but the cache write already happened, and the next daemon cycle trusts it.
- **Suggested fix**: Only update the cache when the GitHub leg specifically succeeded (`results.iter().any(|(n, r)| n == "github" && r.is_ok())`), or re-query GitHub (`get_github_visibility`) after the flip and cache the OBSERVED state.

### F3.6 — [SEVERITY: MEDIUM] `make-public`/`make-private` resolves the repo by basename with first-match-wins; no ambiguity detection
- **Location**: src/main.rs:398-411
- **What**: `repos.into_iter().find(|p| p.file_name() == repo_name)` — if two watched repos share a basename (e.g. `~/Dev/foo` and `~/experiments/foo`), the flip silently targets whichever `discover_git_repos` returns first. The visibility cache is keyed by full-path hash (visibility.rs:65), so only the first repo's cache is updated too.
- **Impact**: Worst case is a privacy incident: `make-private foo` intended for repo A flips repo B instead, or `make-public foo` publishes the WRONG repo to the world. The command prints only the basename in its summary, so the operator may not notice which path was hit.
- **Suggested fix**: Collect ALL matches; if >1, bail with an error listing the full paths and require a disambiguating flag (or accept a full path). Print the resolved full path before flipping.

### F3.7 — [SEVERITY: MEDIUM] `refresh-visibility` reports errors as "refreshed" and poisons the cache to private; `errors` counter is dead
- **Location**: src/main.rs:1206 (`let errors = 0usize;` never incremented), :1245-1248; src/visibility.rs:222-247 (`get_github_visibility` returns `true`/private on ANY error)
- **What**: `get_github_visibility` uses "private" as the safe default for gh-missing/network/auth failures. `refresh-visibility` then does `update_visibility_cache(repo_path, private)` and pushes `{"status": "refreshed"}` — a transient `gh api` outage marks every repo private and reports success. The `errors` JSON field is hardcoded 0.
- **Impact**: After one bad run, the codeberg gate skips codeberg pushes for ALL repos (up to 24h until the next stale refresh), and the operator sees "refreshed N · skipped 0" with no error signal. Same poisoning exists in `sync_mirror_visibility` (visibility.rs:645: cache updated with the safe-default value even when `gh` failed), though that path at least eprintln-warns.
- **Suggested fix**: Change `get_github_visibility` to return `Option<bool>`/`Result<bool>`; on error, skip the cache write and count an error in refresh-visibility (increment `errors`, mark the repo `"error"` in results).

### F3.8 — [SEVERITY: MEDIUM] `parse_github_owner_repo` misparses `ssh://` and userinfo URLs, and accepts non-GitHub origins as GitHub
- **Location**: src/visibility.rs:197-218
- **What**: The SSH branch triggers on ANY URL containing `@` and uses `rfind(':')`:
  - `ssh://git@github.com/DraconDev/repo.git` → `rfind(':')` hits the SCHEME colon → owner=`""`, repo=`"/git@github.com/DraconDev/repo"` (garbage, but `Some`).
  - `https://user:token@github.com/o/r.git` → same scheme-colon trap.
  - `git@gitlab.com:dracondev/repo.git` (origin = gitlab/codeberg — e.g. the nested game submodules whose `.gitmodules` lists codeberg first) → parsed as a GitHub owner/repo pair with no host check; `gh api repos/dracondev/repo` then 404s → safe-default "private" → cache poisoning per F3.7.
- **Impact**: Repos with `ssh://`-form or non-GitHub origins get garbage or wrong-forge visibility lookups; failures feed the private safe-default and the codeberg gate. `flip_repo_visibility` likewise runs its GitHub leg against non-GitHub origins.
- **Suggested fix**: Parse with the same tuple-atomic approach as `ownership::parse_origin` (extract host first, verify it is github.com, then split owner/repo); return `None` for non-GitHub hosts so callers take the explicit "no github origin" branch instead of the safe-default poisoning path.

### F3.9 — [SEVERITY: MEDIUM] `mirror_consecutive_fails` is never populated — the "Mirror Degraded" notification is dead code; PUSH_STUCK error loses the failing remote's name
- **Location**: src/daemon.rs:2198 (field), :2586/:2915 (only ever initialized to `HashMap::new()`), :3322-3340 (consumer — Mirror Degraded notification loop); src/sync.rs:1600-1612, :3039-3063, :3665-3680
- **What**: `push_background` tracks per-remote failures in `remote_failures` (incremented on failure, cleared on success), and the apply phase stores them on the activity entry — but nothing ever copies them into `entry.mirror_consecutive_fails`. Grep confirms zero mutation sites other than initialization. The notification loop iterates a permanently-empty map. Separately, when a MIRROR push fails, `record_push_failure(repo, "git push returned non-zero (see daemon log)")` conflates it with origin failures in the same `consecutive_failures` counter and the generic message reaches `repos` as the PUSH_STUCK reason (report.rs:2865-2873) — the operator can't tell WHICH remote is failing without reading the journal.
- **Impact**: A chronically-failing mirror (e.g. codeberg quota, dead gitlab token) never triggers the intended desktop notification; the repo eventually shows PUSH_STUCK with an opaque "git push returned non-zero" message even when origin pushes are healthy, and `is_repo_stuck` then blocks manual `sync-now` (main.rs:807-813) for a repo whose origin is fine.
- **Suggested fix**: Either populate `mirror_consecutive_fails` from `remote_failures` in the apply phase, or delete the dead field+loop. Pass the failing remote name(s) into `record_push_failure`'s error string (e.g. `format!("push to {} failed: {}", name, e)` from push_background's result list).

### F3.10 — [SEVERITY: MEDIUM] F52 control-character check covers only the env-var path; `.env`-file secrets are unvalidated (curl header injection surface)
- **Location**: src/secrets.rs:32-50 (check), :80-100 (file path, no check); sink: src/visibility.rs:272,331,716,773 (`format!("PRIVATE-TOKEN: {}\r\n", token)` / `Authorization: token {}\r\n` written to curl stdin)
- **What**: F52 (2026-07-18) refuses env-var values containing control chars, but `load_secret_from_dir` returns file-loaded values verbatim. A mid-line `\r` survives `str::lines()` (only a TRAILING `\r` is stripped), so `GH_TOKEN=abc\rX-Injected: yes` in a `.env` file produces a token containing `\r`, which is then interpolated into an HTTP header block passed to `curl -H @-`. Also unhandled common `.env` forms: `KEY="quoted"` keeps the literal quotes, and `KEY=abc # comment` keeps the comment — both produce silently-failing tokens.
- **Impact**: A corrupted (or maliciously-modified, in a shared-home scenario) secrets file can inject extra curl headers or silently break auth with no diagnostic. The F52 protection is half-applied.
- **Suggested fix**: Apply the same `c.is_control()` refusal in `load_secret_from_dir` before returning a value; optionally strip surrounding matching quotes and unquoted trailing comments per `.env` convention.

### F3.11 — [SEVERITY: LOW] Trust matching is exact case-sensitive despite policy comment claiming caller-side case-insensitivity
- **Location**: src/ownership.rs:294-310 (`is_trusted_origin`: `th == host && to == owner`), :179-181 (emails), :212-218 (author names); src/policy.rs:1130-1133 (comment: "Case-insensitive matching is left to the caller")
- **What**: The F39 tuple-atomic fix is correctly implemented (verified: `DraconDev.evil.com`, `@` in path, userinfo, port, trailing `.git`/`/` all handled), but matching is byte-exact. The defaults enumerate exactly two casings (`DraconDev`/`dracondev`); a URL like `git@github.com:Dracondev/r.git` or host `Github.com` → false `untrusted_origin` → repo skipped. Same for `DRACSHARP@gmail.com` vs `dracsharp@gmail.com` (exact `e == email`). The policy.rs comment describes case-insensitive matching that no caller implements.
- **Impact**: Fail-safe direction (skip, not push-to-attacker) but operator-visible false Unowned classifications, and a misleading comment that may lead a future editor to remove the duplicated-case defaults.
- **Suggested fix**: Normalize with `to_ascii_lowercase()` on host and owner (forge names are case-insensitive) and on emails at `TrustedSet` construction; fix the comment.

### F3.12 — [SEVERITY: MEDIUM] `matches_untracked_exclude`: relative-path patterns without `**` silently match nothing; `rel.contains()` substring overmatch
- **Location**: src/exclude.rs:948-993
- **What**: Two issues:
  1. A pattern containing `/` but neither starting with `**/` nor containing `/**` (e.g. `reports/kdp-live-*.md` — the exact pattern class AGENTS.md documents for rust-ai-web-auto) falls through BOTH branches: the basename branch requires `!pattern.contains('/')`, the glob branch requires `**/`. The pattern is silently dead — files the operator wanted excluded get auto-committed, with no warning.
  2. The glob branch uses `rel.contains(pattern.trim_start_matches("**/").trim_end_matches("/**"))` — a raw substring test. `**/scratch/**` excludes `docs/unscratched/notes.md` and `src/scratchpad.rs`; `**/~/**` (a live default, policy.rs:1010) excludes ANY path containing a tilde (e.g. `notes/~draft.md`); `**/tmp/**` excludes `foo/tmpl/x`. Those files are then never auto-committed, silently, contradicting the commit-all principle.
- **Impact**: (1) silent config failure in the "things get committed that shouldn't" direction; (2) silent under-commit in the "nothing left out" direction. Both are invisible to the operator.
- **Suggested fix**: For (1), route single-`/`-prefixed relative patterns through the segment matcher (or warn on unrecognizable pattern shapes in `validate_config`). For (2), drop the raw `contains` arm — the segment-wise `matches_file_pattern` fallback below it already implements the intended semantics.

### F3.13 — [SEVERITY: LOW] role.rs: F55 "prefer full-path" comment not implemented — basename/path-tail fallbacks still misclassify
- **Location**: src/role.rs:147-169
- **What**: The F55 comment says full-path equality is tried FIRST and basename is a LAST RESORT, but the code is a flat `if full_path_matches || name_matches || path_tail_matches`. A standalone watched repo whose basename happens to equal another parent's submodule `name` or path-tail (e.g. a revived `/Dev/junk-runner` standalone next to `dracon-platform`'s `web/games/wip/junk-runner`) is still classified `Submod`. Display-only (ROLE column).
- **Suggested fix**: Implement the stated precedence: check full-path equality across all parents first; only if no full-path match exists, apply name/path-tail fallbacks.

### F3.14 — [SEVERITY: LOW] bump.rs: `version = "1.2.3" # comment` parses to None — version silently not bumped
- **Location**: src/bump.rs:10-14
- **What**: The manual parser requires the value to END with `"` (after optional `;`). An inline comment after the version string — legal and common in Cargo.toml — makes `strip_suffix('"')` fail → `extract_version_from_cargo` returns None → the auto-bump silently skips that repo's Cargo.toml.
- **Suggested fix**: After stripping the opening `"`, take everything up to the NEXT `"` instead of requiring the line to end with `"`; add a test with a trailing comment.

### F3.15 — [SEVERITY: LOW] report.rs ledger/in-flight minors: wrong pruned-count in >100MB branch; non-atomic ledger rewrite; stale doc constant
- **Location**: src/report.rs:1091-1104 (returns `Ok(lines.len())` = kept lines, while the normal branch returns removed count — the startup log "🧹 pruned {} stale incident entries" is wrong on the truncation path), :1132 (whole-file rewrite without temp+rename — a crash mid-write truncates the ledger), :713 vs :740 (doc comment says `IN_FLIGHT_MAX_AGE_SECS` default 30s; the const is 5s)
- **Impact**: Misleading operator logs, small ledger-loss window on crash, stale documentation.
- **Suggested fix**: Return `original - kept` consistently; write to `<path>.tmp` + rename; fix the comment.

## Summary

1. **HIGH**: The v0.112.29 multi-placeholder `str::replace` bug survives in `CODEBERG_API_REPOS` — every Codeberg visibility/metadata API call builds a doubled URL and 404s; the pinning test added for GitLab has no Codeberg twin (F3.1).
2. The TOML footgun is live TODAY in the operator's own config (`standard_files_auto` silently absorbed into the last `[[standard_files]]` entry, verified by parsing the live file), and the detector's `in_table` logic plus `config validate`'s warning suppression conspire to hide it (F3.2, F3.3).
3. `expand_tilde("~/x") → /x` (verified by compiling the function), fragile `parse_github_owner_repo`, and safe-default poisoning in `refresh-visibility`/`handle_visibility_flip` all erode the visibility cache that drives the codeberg public-only gate (F3.4-F3.8).
4. `mirror_consecutive_fails` is permanently empty — the Mirror-Degraded notification can never fire, and mirror failures surface only as an opaque PUSH_STUCK (F3.9); the F52 control-char guard covers env vars but not `.env` files feeding curl header interpolation (F3.10).
5. Lower-severity: case-sensitivity comment/impl mismatch in trust checks (fail-safe), dead-pattern and substring-overmatch traps in exclude.rs, and display/doc minors in role.rs, bump.rs, report.rs (F3.11-F3.15).

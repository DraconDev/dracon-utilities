## Findings

### F4.1 — [SEVERITY: HIGH] harden_repo wipes all operator .gitignore / .gitattributes rules outside the managed block
- **Location**: dracon-warden/src/main.rs:1103-1108 (call sites), 660-696 (`apply_overwrite_file`), 568-613 (`build_gitignore_block_with_existing`)
- **What**: `harden_repo` writes `.gitignore` via
  `apply_overwrite_file(path, build_gitignore_block_with_existing(policy, &existing))`.
  `build_gitignore_block_with_existing` returns ONLY the managed block
  (it preserves patterns from *inside* the existing managed block, not
  operator content outside it), and `apply_overwrite_file` overwrites the
  ENTIRE file with that block. Same for `.gitattributes`
  (`build_gitattributes_block` doesn't even look at existing content).
  The surgical merge function that would preserve surrounding content,
  `replace_managed_block`, exists but is `#[cfg(test)]`-only
  (main.rs:489) — production never uses it.
- **Evidence**: live git history of this meta-repo:
  - `b69d9c2c` (4 weeks ago): operator added an 8-line custom section
    (`/dracon-sync/`, `/dracon-system/`, `/dracon-warden/` excludes)
    after the managed block.
  - `3a67685f` (3 weeks ago, "DELTA:+0/-8"): a warden harden pass
    deleted exactly those 8 lines, leaving only the managed block.
  - `e1490e10` (2026-07-15): operator re-added the section
    ("NESTED STANDALONE REPOS (NOT warden-managed)"). It is still
    present only because no harden pass has run on this repo since;
    the next `dracon-warden once` will delete it again.
- **Impact**: silent deletion of operator gitignore rules on every
  harden pass. In this repo the wiped rules keep the 3 nested
  standalone repos out of the parent — losing them re-triggers the
  scan-bloat flags (v0.112.15) and risks the daemon treating nested-repo
  files as parent content. Contradicts the policy's own doc: "The
  manager surgically edits .gitignore ... using markers."
- **Suggested fix**: make `harden_repo` use `replace_managed_block`
  semantics for both files (promote it out of `#[cfg(test)]`): replace
  only the delimited block, preserve everything outside it, append the
  block if absent. Keep `apply_overwrite_file`'s atomic temp+rename for
  the final write. Add a regression test: pre-existing `.gitignore`
  with content before AND after the block survives `harden_repo`
  unchanged except inside the block.

### F4.2 — [SEVERITY: HIGH] smudge corrupts whole-file-encrypted binary content via `String::from_utf8_lossy`
- **Location**: dracon-warden/src/security/src/modules/filter.rs:361
  (`smart_smudge`), encrypt side filter.rs:318 / lib.rs:779
- **What**: `smart_clean_with_path` whole-file-encrypts binary files in
  sensitive locations as a base64 text tag (`[DRACON_SECRET:<b64>]`,
  filter.rs:311-319). The matching decrypt path, `smart_smudge`, is a
  `&str -> String` transform: after successful decryption it does
  `result.push_str(&String::from_utf8_lossy(&plaintext))`. If the
  original plaintext was not valid UTF-8 (e.g. a DER `.key`, a SQLite
  file under `secrets/**`, a `.kdbx`), every invalid byte sequence is
  replaced with U+FFFD — the working-tree file is silently corrupted.
- **Evidence**: `DraconWarden::smudge` (lib.rs:1505) only short-circuits
  when the *stored* bytes contain a NUL (`is_binary_content`); the
  stored form is ASCII text (`[DRACON_SECRET:...]`), so the binary
  passthrough never triggers for whole-file-encrypted content. Protected
  patterns in the live policy (`~/.dracon/utilities/warden/dracon-warden.toml`)
  include `secrets/**`, `*.key`, `*.pem`, which intersect the binary
  sensitive-extension list (`.sqlite`, `.kdbx`, `.sql`, DER `.key`...).
- **Impact**: irreversible data corruption of binary secret files. Worse:
  the corrupted working-tree file is later re-cleaned and re-encrypted,
  so the corruption propagates into git history and the original bytes
  are lost (only the pre-encryption backup in `.git/arcane/backups`
  would retain them, and `backup_secret` only fires for `.env` paths in
  `seal_clean`).
- **Suggested fix**: make whole-file-encrypted payloads round-trip as
  bytes, not strings. Detect a whole-file tag
  (`starts_with_any_secret_tag` already exists), and if the ENTIRE
  content is one tag, decrypt and write the raw plaintext bytes to
  stdout without UTF-8 conversion. Reserve `from_utf8_lossy` for inline
  tags embedded in otherwise-textual content (and even there, document
  that binary-capable secrets must use whole-file encryption). Add a
  round-trip test: random non-UTF-8 bytes in `secrets/blob.sqlite` →
  clean → smudge → byte-identical.

### F4.3 — [SEVERITY: MEDIUM] `allow_v1_fallback` gate is not wired — V1 ciphertexts are undecryptable and the documented migration path does not exist
- **Location**: dracon-warden/src/security/src/lib.rs:42-50
  (`set_allow_v1_fallback`), crypto.rs:280-286 (gate), main.rs:290-306
  (`WardenPolicy` struct)
- **What**: FDRACONWARDEN-001's remediation kept a runtime escape hatch
  "for one migration cycle" and its comment says: *"set
  `allow_v1_fallback = true` in the policy, decrypt once to re-encrypt
  under V2"*. But `set_allow_v1_fallback` has ZERO callers in the
  workspace (verified by grep), and `WardenPolicy` has no
  `allow_v1_fallback` field (serde ignores unknown TOML keys, so adding
  it to the policy file silently does nothing). `monorepo-README.md:175`
  also documents `allow_v1_fallback = false` as a policy knob.
- **Impact**: any operator with legacy V1 (AES-CFB) ciphertexts cannot
  decrypt them at all — `decrypt_git_seal` always errors, and
  `unlock_payload` falls through to "Decryption failed after trying all
  keys". The promised one-cycle recovery window is inaccessible; when
  v0.113 removes the gate, those ciphertexts become permanently
  unrecoverable.
- **Suggested fix**: add `allow_v1_fallback: bool` (serde default
  false) to `WardenPolicy` and call `set_allow_v1_fallback(policy.allow_v1_fallback)`
  at policy load in every command that can reach `unlock_payload`
  (filter-smudge, resmudge, repair). Alternatively expose an explicit
  CLI flag (`dracon-warden repair --allow-v1`) scoped to a single
  process so the hatch cannot be left on permanently.

### F4.4 — [SEVERITY: MEDIUM] `setup-hooks --local` runs `git config local core.hooksPath <dir>` — missing `--`, always fails
- **Location**: dracon-warden/src/main.rs:2342
- **What**: the Local branch of `run_setup_hooks` builds:
  `.args(["config", "local", "core.hooksPath", &dir.to_string_lossy()])`.
  Without the `--` prefix, git parses this as
  `git config <name> <value> <extra>` = "wrong number of arguments",
  so the command exits non-zero and `run_setup_hooks` returns an error
  every time. This is exactly the bug class of this week's dracon-sync
  test incident (positional arg to `git config`), except here it is in
  production code, not a test.
- **Evidence**: compare with the correct global branch two dozen lines
  earlier (`.args(["config", "--global", "core.hooksPath", ...])`,
  main.rs:2315) and with `ensure_repo_filter_config` (main.rs:928-935,
  correct `--local`).
- **Impact**: `dracon-warden setup-hooks --local` can never succeed;
  the hooks are written to `.git/hooks/` but `core.hooksPath` is never
  set, and the operator gets a confusing "failed to set local
  core.hooksPath: error: wrong number of arguments" after the hook
  files were already written (partial application).
- **Suggested fix**: change `"local"` to `"--local"`. Add a behavioral
  test that runs `run_setup_hooks(HookMode::Local, ...)` against a temp
  repo and asserts `git -C repo config --local --get core.hooksPath`
  succeeds. (The existing pre-push hook tests show the pattern.)

### F4.5 — [SEVERITY: MEDIUM] filter-clean silently passes through plaintext for >10 MiB inputs and for refused paths
- **Location**: dracon-warden/src/main.rs:2134-2137 (size guard),
  2144-2163 (path refusal), 2092 (`STREAM_IO_MAX_BYTES`)
- **What**: `run_filter` returns the input unchanged (exit 0) in two
  cases: (1) input exceeds 10 MiB, (2) the `%f` path failed the
  FDRACONWARDEN-002 validation (absolute or `..`). For filter-SMUDGE,
  passthrough is correct (keeps ciphertext as-is). For filter-CLEAN,
  passthrough means the file is committed to git UNENCRYPTED — a 15 MiB
  `.env` (or any oversized protected file) lands in history in
  plaintext with no warning. The module's own doc comment
  (main.rs:33-38) states the opposite principle for the timeout path:
  "returning passthrough would silently corrupt data".
- **Impact**: plaintext secret leak into git history, silent. The
  pre-push hook is the only backstop, and it has its own gaps (F4.6).
- **Suggested fix**: in the clean direction, fail closed (exit non-zero
  with a stderr message) for oversized inputs and refused paths; git
  aborts the add and the operator sees why. If large files legitimately
  need support, stream the encryption (age supports streaming) instead
  of the 10 MiB read_to_end cap. Keep passthrough only for smudge.

### F4.6 — [SEVERITY: MEDIUM] pre-push hook word-splits filenames — paths with spaces bypass the secret scan
- **Location**: dracon-warden/src/main.rs:2262-2281 (`PRE_PUSH_HOOK`)
- **What**: the hook iterates `for f in $(git diff --name-only "$RANGE")`,
  which word-splits on whitespace. A file named `prod secrets.env` is
  split into `prod` and `secrets.env`; neither fragment has a
  `.plaintext` sibling, so both are appended to `SCAN_FILES`, and the
  later `git diff --unified=0 "$RANGE" -- $SCAN_FILES` (also unquoted)
  matches nothing for the real path → the file's added lines are never
  scanned → a plaintext secret in a space-containing filename pushes
  clean. Filenames with glob metacharacters are additionally expanded
  by the unquoted `$SCAN_FILES`.
- **Impact**: the defense-in-depth pre-push scan silently misses exactly
  the files most likely to be ad-hoc secret drops ("my secrets.txt").
  The primary filter-clean protection still applies to protected
  patterns, but `--no-verify`/misconfigured-filter bypasses (the
  scenario this hook exists for) go undetected for such files.
- **Suggested fix**: use NUL-delimited iteration:
  `git diff --name-only -z "$RANGE" | while IFS= read -r -d '' f; do ...`
  and pass collected files via `git diff ... -- "$@"`-style positional
  params or a `-z` pathspec (`--pathspec-from-file=- --pathspec-file-nul`).
  Add a hook behavioral test with a filename containing a space and an
  added `AKIA...` line, asserting exit 1.

### F4.7 — [SEVERITY: MEDIUM] guard's active-build protection misses workspace members — target/ deleted mid-build
- **Location**: dracon-system/src/main.rs:790-800 and 895-907
  (protected-dir walk), 820 / 934 (`target_project == proj` check)
- **What**: before deleting a Rust `target/` dir, the guard protects
  projects with a running cargo/rustc by walking up from the process
  CWD to the FIRST ancestor containing a `Cargo.toml`. In a cargo
  workspace, running `cargo build` from a member crate
  (`ws/crates/foo`) stops at the member's own `Cargo.toml`, but the
  shared target dir lives at the WORKSPACE root (`ws/target`). The
  exact-equality check `target_project == proj` then fails, and
  `ws/target` is deleted while the build is writing to it. Same gap
  for `cargo build --manifest-path ...` run from an unrelated CWD.
- **Impact**: not data loss, but hours of recompilation and potential
  cargo lock corruption/races when the guard's auto-cleanup or
  proactive-cleanup fires during a big workspace build. The protection
  is the ONLY thing standing between the guard and an active build
  (comment at main.rs:779: "ONLY protection mechanism").
- **Suggested fix**: walk up ALL ancestors collecting every dir with a
  `Cargo.toml` (or better: parse `[workspace]` / the `workspace` key
  upward to find the workspace root), and protect a target dir if its
  project dir is an ancestor-or-equal of any protected dir
  (`proj.starts_with(target_project)` or vice versa). Cheaper: treat a
  target dir as active if its mtime is < N seconds old (builds touch it
  constantly) — the code already computes `mtime_secs_ago` but only the
  proactive path uses it.

### F4.8 — [SEVERITY: MEDIUM] hostile newlines in process argv inject fake `ps` lines — guard can renice an arbitrary victim PID
- **Location**: dracon-system/src/main.rs:438-462 (`parse_ps_output`),
  476-492 (`process_samples`)
- **What**: `ps -eo pid,ppid,pcpu,rss,comm,args` prints argv raw, and a
  process can embed `\n` in its arguments. `parse_ps_output` then treats
  the injected text as additional `ps` rows. A local process with argv
  containing e.g. `"\n1234 1 999.0 9999999 x"` fabricates a heavy-process
  sample for PID 1234; after the sustain window the guard renices PID
  1234 — an innocent victim (renice values are clamped 0..19, so it can
  only deprioritize, and the guard never kills — this bounds the blast
  radius). Related latent issue on the same path: the renice itself has
  no process-identity check, so a PID recycled during the sustain window
  gets reniced (the PID-recycle guard at main.rs:1975-1999 only covers
  the UN-renice path).
- **Impact**: local unprivileged process can cause the guard to renice
  arbitrary PIDs (e.g. the operator's editor or the dracon-sync daemon).
  Requires local code execution; effect is reversible scheduling
  priority, so MEDIUM not HIGH.
- **Suggested fix**: before acting on a sample, verify the PID's
  identity out-of-band: read `/proc/<pid>/comm` and require it to equal
  the sampled `command` (cheap, kills the injection because the injected
  row's pid/comm pair won't match a real process), and record
  `/proc/<pid>/stat` starttime at first sight, re-checking it before
  renice to close the PID-reuse window. Alternatively parse `ps` with
  `args` LAST (already the case) and reject any sample whose PID was
  not seen in a `pid,comm`-only authoritative listing.

### F4.9 — [SEVERITY: MEDIUM] security-subcrate test guards drop the env mutex immediately — parallel tests race on HOME
- **Location**: dracon-warden/src/security/tests/common.rs:13 and :51
- **What**: both `HomeGuard::new` and `EnvRestorer::new` do
  `let _lock = ENV_MUTEX.lock()...;` — a LOCAL binding that is dropped
  when `new()` returns. The mutex is therefore held only during the
  `set_var` call itself, NOT for the guard's lifetime. Every test in
  this binary that sets HOME runs in parallel with every other,
  mutating process-global HOME concurrently (the main crate's tests.rs
  HomeGuard correctly stores the `MutexGuard` in the struct — this file
  does not). This is the same class as daemon F45/F46 (racy env restore),
  which was fixed in v0.112.21 for dracon-sync but persists here.
  Secondarily, `Drop` does `remove_var` then `set_var`, leaving HOME
  briefly unset for racing readers.
- **Impact**: flaky/nondeterministic security-subcrate tests (identity
  loading, backup roots, keychain paths all read HOME), and — because
  `WardenSecurity::get_or_init` caches identities in a `OnceCell` keyed
  by whatever HOME was at first init — cross-test contamination where a
  test silently uses the REAL operator keyring cached by an earlier
  test. No production impact.
- **Suggested fix**: store the `MutexGuard<'static, ()>` in both guard
  structs (mirror the main crate's HomeGuard), and restore the old
  value before removing (or just `set_var`/overwrite directly) to avoid
  the unset window. Consider serializing with a `#[serial_test]`-style
  annotation as belt-and-braces.

### F4.10 — [SEVERITY: LOW] `is_git_tracked_dir` checks the basename at the repo ROOT — nested tracked dirs misdetected as untracked
- **Location**: dracon-system/src/main.rs:2388-2445
- **What**: to decide whether a hotspot dir (e.g. `repo/sub/proj/target`)
  is git-tracked, the function resolves the toplevel from the dir's
  PARENT, then runs `git -C <repo_root> ls-files -- <basename>` — the
  basename only (`target`), evaluated at the repo root. A nested tracked
  dir (`repo/web/node_modules`) only matches if the root itself tracks a
  same-named entry. Result: tracked nested dirs are reported
  "untracked" and `storage --cleanup --apply` deletes them without
  requiring `--allow-tracked`.
- **Impact**: deletion of git-tracked content (recoverable via git, but
  surprising and against the flag's contract). Inverse false positives
  (a root-level tracked `target` marking every nested `target` as
  tracked) cause skips — noise only.
- **Suggested fix**: compute the path relative to the resolved toplevel
  (`path.strip_prefix(&repo_root)`) and pass THAT to `ls-files --`.

### F4.11 — [SEVERITY: LOW] per-repo hooks installed by harden are inert when the global hooksPath is set
- **Location**: dracon-warden/src/main.rs:2372-2406 (`install_hooks_for_repo`),
  called from `harden_repo` at :1115
- **What**: `harden_repo` writes `pre-commit`/`pre-push` into each
  repo's `.git/hooks/`, but `setup-hooks` (global, the default) sets
  `core.hooksPath=~/.config/git/hooks`, which makes git IGNORE
  `.git/hooks` entirely in every repo. On any machine that ran
  `setup-hooks --global`, the per-repo hook installation is dead code —
  silently.
- **Impact**: misleading hardening signal ("hooks installed" but never
  executed); the global hooks currently provide equivalent coverage, so
  no protection gap today, but an operator who deletes the global
  hooksPath believing per-repo hooks exist loses the pre-push net.
- **Suggested fix**: either drop `install_hooks_for_repo` when a global
  hooksPath is configured (check `git config --get core.hooksPath`),
  or document that per-repo hooks are a fallback for machines WITHOUT
  the global setup.

### F4.12 — [SEVERITY: LOW] `load_system_policy` swallows read errors — guard daemon runs on defaults when the policy exists but is unreadable
- **Location**: dracon-system/src/main.rs:2314-2327
- **What**: if the resolved policy path exists but `read_to_string`
  fails (permissions, I/O), the function returns
  `(Some(path), SystemPolicy::default())` with the error DISCARDED
  (`Err(_e)`). Parse errors ARE surfaced; read errors are conflated
  with "no policy". The SIGHUP reload path then replaces the live guard
  config with defaults (auto_cleanup_apply=false is safe, but
  thresholds/marker paths silently change).
- **Impact**: operator edits/chmods a policy file, guard silently runs
  on defaults; disk thresholds and the sync-freeze marker path may
  diverge from what the operator believes is active.
- **Suggested fix**: propagate the read error (`with_context`) the same
  way parse errors are propagated; let the daemon keep the OLD policy
  on reload failure (it already logs and continues for parse errors).

## Summary

Two HIGH findings in warden: `harden_repo` overwrites whole
.gitignore/.gitattributes and provably deleted operator rules in this
repo's own history (commit 3a67685f), and `smart_smudge` lossy-UTF-8
conversion corrupts whole-file-encrypted binary secrets on checkout.
One v0.112.21 fix is incomplete: the V1 fallback gate exists but is
unreachable (no policy field, no callers). dracon-system shows the
same bug-pattern family as the daemon: a positional `git config` arg
(setup-hooks --local), a workspace-aware cache/protection gap in
target-dir cleanup, and ps-output parsing vulnerable to argv newline
injection. Warden's security-subcrate tests repeat the env-mutex race
the daemon fixed in F45/F46. No plaintext-through-filter path was found
for the normal (small, valid-path) case: clean fails closed on
encryption errors; the leaks are the >10 MiB passthrough and the
word-split pre-push hook.

Findings: 12 total — 2 HIGH, 7 MEDIUM, 3 LOW.

# Audit 2026-07-21 — Part 0: Live incident (test pollution + ownership cache)

> Written during the audit kickoff. The user's `repos` output showed the
> daemon's OWN source repo as `🚫 unowned` with 2 stuck modified files.
> Root-caused and repaired live before the audit agents were spawned.
> This incident is itself the audit's first two findings.

## Incident timeline (2026-07-21)

1. **~14:20** — A v0.112.30 test I added
   (`test_has_codeberg_tracking_ref_present_after_update_ref` in
   `multi_remote.rs`) ran:
   ```rust
   std_git_command().args(["config", "user.email", "test@test"]).arg(&repo)
   ```
   The repo path was passed as a POSITIONAL arg, which git interprets
   as `git config <name> <value> <value-pattern>` — setting the config
   in the repo at the **process CWD**. Under `cargo test` the CWD is
   the real `dracon-sync/` package root, so the test wrote
   `user.email = test@test` and `user.name = test` into the LIVE
   repo's `.git/config`. Multiple test runs = multiple values
   ("user.email has multiple values").
2. **~14:25** — The daemon auto-committed pending v0.112.30 changes
   with the poisoned identity: commit `35a72d7` authored
   `test <test@test>`, pushed to all 3 mirrors.
3. **~14:30** — The ownership guard (F44/F39 hardening) read
   `user.email = test@test` (untrusted) and flipped the repo to
   🚫 unowned, refusing all further sync — **correct behavior**;
   the guard did exactly what it was designed to do.
4. **~15:00** — User reported the 🚫 unowned row.

## Repair (all verified live)

1. Fixed the test to use `.current_dir(&repo)` for config calls;
   added a comment explaining the hazard.
2. Grepped the workspace for the same pattern
   (`.args(&args).arg(`, bare `Command::new("git")` + config) — no
   other instances; existing tests use `-C` or `current_dir`.
3. `git config --unset-all user.email / user.name` in the nested
   repo (multiple values had accumulated).
4. Made a manual commit with explicit trusted identity
   (`git -c user.email=dracsharp@gmail.com -c user.name=DraconDev`)
   so HEAD author is trusted again — forward-only, no history
   rewrite (commit `5e32547`; the `test@test` commit `35a72d7`
   remains in history on all mirrors, which is acceptable: the
   content is correct, only the author string is wrong).
5. Manually pushed `5e32547` to origin/gitlab/codeberg (daemon
   was still skipping the repo — see F0.2).
6. Sent SIGHUP to the daemon → ownership re-detected → daemon
   committed the remaining change (`b872aea`) and pushed.

## Findings

### F0.1 — [SEVERITY: HIGH] Test-infrastructure hazard: git commands in tests can mutate the LIVE repo
- **Location**: `dracon-sync/src/git/multi_remote.rs` (test,
  fixed in commit `5e32547`)
- **What**: `git config <name> <value> <path>` (path as positional
  arg) sets config in the repo at the process CWD, not at `<path>`.
  Under `cargo test`, CWD = the real package root. Any test that
  runs git with a positional path instead of `-C <path>` /
  `current_dir` can silently mutate the live repo's config, index,
  or refs.
- **Impact**: live repo knocked into unowned state (sync refused);
  daemon committed with a poisoned identity; mirrors carry a
  `test@test` commit.
- **Fix applied**: test rewritten with `current_dir` + explanatory
  comment; workspace grep clean.
- **Follow-up**: add a CI guard or lint — e.g. a test-only wrapper
  (`test_git_cmd`) that FORBIDS positional repo paths on
  config/ref-mutating subcommands, or a pre-push hook that rejects
  commits authored by `test@test` / `test@test.com`.

### F0.2 — [SEVERITY: MEDIUM] Ownership verdict cached indefinitely — operator remediation never detected
- **Location**: `dracon-sync/src/daemon.rs:2591-2620`
- **What**: `RepoActivity.ownership` is populated once
  (`if entry.ownership.is_none() { detect }`) and the entry
  persists across cycles in the loop-level `activity` HashMap. When
  the verdict is Unowned, the loop `continue`s BEFORE any
  `activity.remove` site, so the verdict is never re-evaluated.
  Verified live: after cleaning the config AND landing a
  trusted-author commit, the daemon kept skipping the repo for
  ~25 minutes until SIGHUP (which calls `activity.clear()`).
- **Impact**: an operator who fixes the underlying ownership issue
  (bad user.email, wrong origin) sees the repo stuck at
  🚫 unowned forever, with no hint that a daemon restart/SIGHUP is
  required. The skip log
  (`🚫 ... skipping (untrusted_email): ...`) does not mention the
  cache.
- **Suggested fix**: re-detect ownership on a TTL (e.g. every
  5-15 min per repo while the verdict is Unowned — the 4 git
  subprocess calls are cheap at that cadence), AND/OR extend the
  skip log with "verdict cached; after fixing, run
  `kill -HUP $(systemctl --user show dracon-sync -p MainPID --value)`
  or restart the daemon". A TTL also self-heals repos whose
  ownership flips for other reasons (operator re-clones from a
  different account).
- **Workaround (documented)**: SIGHUP clears the cache:
  `kill -HUP $(systemctl --user show dracon-sync.service -p MainPID --value)`.

### F0.3 — [SEVERITY: LOW] Daemon identity is whatever the repo config says — no self-check before committing
- **Location**: commit path (`sync.rs::stage_commit_and_push` →
  `svc.commit`)
- **What**: the daemon commits with the repo's effective
  `user.email`/`user.name`. When that identity is poisoned (F0.1)
  the daemon happily commits as `test <test@test>` — the ownership
  guard then locks the repo out AFTER the damage is already on the
  mirrors.
- **Suggested fix**: before auto-committing, verify the effective
  committer identity is in `trusted_emails`/`trusted_authors`
  (the same TrustedSet the ownership guard uses); if not, skip the
  commit and surface a WARN ("repo git identity untrusted — not
  committing"). This turns the post-hoc lockout into a pre-commit
  guard. Note: must be careful to reuse the ownership cache rather
  than adding per-cycle subprocess calls (F0.2's TTL covers this).

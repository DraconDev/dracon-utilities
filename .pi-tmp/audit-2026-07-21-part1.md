# Audit Part 1: daemon.rs + sync.rs (2026-07-21)

Scope: `dracon-sync/src/daemon.rs` (3528 LOC) and `dracon-sync/src/sync.rs` (8205 LOC),
read end-to-end at commit `b872aea` (post-v0.112.30). Helper functions in `src/git/` and
`src/exclude.rs` were read only where needed to confirm cost/semantics of call sites in
the two in-scope files. This supersedes/overlaps `audit-part1-sync-daemon-git.md`
(2026-07-18) for these two files; findings below are all re-verified against current code.

## Findings

### F1.1 — [SEVERITY: HIGH] All throttled notifications fire exactly ONCE per daemon lifetime (cooldown map never expires)
- **Location**: daemon.rs:2230 (map), inserts at 2613, 2677, 3121, 3292, 3309, 3326; false claim at 3280 ("rate-limited to 30 min")
- **What**: Every notification throttle uses the same pattern:
  ```rust
  if let std::collections::hash_map::Entry::Vacant(e) = remote_notify_cooldowns.entry(notify_key) {
      // ... send notification ...
      e.insert(Instant::now() + Duration::from_secs(1800));
  }
  ```
  The stored `Instant` deadline is **never read**. No code path checks `now > deadline`,
  no `.retain()` prunes expired entries, and SIGHUP reload (daemon.rs:2296-2300) does not
  clear the map. Once a key is inserted it is `Occupied` forever, so the `Vacant` branch
  never fires again.
- **Evidence**: `grep -n remote_notify_cooldowns src/daemon.rs` → 7 hits, all inserts/reads
  via `Entry::Vacant`; zero expiry checks. Affects: ownership-skip reminder, stuck-retry
  alert, push-failure notification, Stuck-Ahead, Stuck-Behind, Mirror-Degraded.
- **Impact**: A repo stuck ahead for 3 days produces ONE desktop notification at the
  10-minute mark, then silence forever (until daemon restart). The operator's only repeated
  signal for a persistently failing repo is gone; the 1800s constant is dead code.
- **Suggested fix**: Replace the `Entry::Vacant` pattern with a get-and-compare:
  `if map.get(&key).is_none_or(|until| now >= *until) { notify(); map.insert(key, now + 1800s); }`.
  Also clear the map on SIGHUP for consistency with the other cooldown maps.

### F1.2 — [SEVERITY: HIGH] Stuck-push ledger split-brain: in-memory map never sees runtime failures; retry resets the failure budget; `push_max_retries` never enforced
- **Location**: daemon.rs:2231 (load-once), 2659-2691 (skip/retry), 1660-1680
  (`record_push_failure` — disk only), sync.rs:3058-3070, 3667-3678 (call sites)
- **What**: Three interlocking defects around `stuck_push_repos`:
  1. The daemon loop's map is loaded **once at startup** (line 2231). `record_push_failure`/
     `record_push_success` (called from spawned sync tasks) load → mutate → save the **disk
     file** only. Runtime-recorded failures are therefore invisible to the loop's
     `stuck_push_repos.get(&repo)` skip check — the documented "skip for 5 min, then retry"
     backoff never fires for any repo that gets stuck after daemon start.
  2. When the retry path DOES fire (startup-loaded entries only), it removes the entry from
     the map **and disk** (line 2689-2690) before dispatching. When the retry fails,
     `record_push_failure` creates a fresh entry with `consecutive_failures = 1`
     (`or_insert_with`, line 1664-1676). The consecutive-failure budget is thus reset on
     every 5-minute retry cycle and can never accumulate.
  3. `push_max_retries` is not consulted anywhere in daemon.rs or sync.rs — only in
     report.rs:2812 (display). The `StuckRepoEntry` doc comment ("used to detect when the
     retry budget is exhausted and the daemon should stop auto-pushing") describes behavior
     that does not exist: the daemon auto-pushes forever regardless of failure count.
- **Evidence**: `grep -n "push_max_retries" src/` → policy def + report.rs display only;
  `grep -n "stuck_push_repos" src/daemon.rs` → no `.insert` outside tests and load.
- **Impact**: The entire stuck-push escalation story is illusory at runtime: no 5-min
  backoff for fresh failures, no budget exhaustion, no auto-push stop. The report's
  `🛑 push-stuck` HINT can appear while the daemon is in fact still pushing every cycle.
- **Suggested fix**: Have `record_push_failure`/`record_push_success` operate on the
  daemon's shared map (or reload the ledger into the loop map each cycle — it is a tiny
  JSON file), do NOT delete the entry before a retry (mark `last_retry_at` instead), and
  gate dispatch on `consecutive_failures < policy.push_max_retries` in the per-repo loop.

### F1.3 — [SEVERITY: HIGH] Push failure is reported as success: `Synced` / "🔁 synced" after a failed push defeats all daemon-side failure accounting
- **Location**: sync.rs:3036-3070 (`stage_commit_and_push` push block → falls through to
  `Ok(None)` → `SyncOutcome::Synced` at 3633); sync.rs:3661-3684 (`handle_ahead_push` →
  `Ok(())` → `NothingToDo`); daemon.rs:3086-3151 (apply phase)
- **What**: When the push fails, `stage_commit_and_push` calls `record_push_failure` (disk
  ledger only — see F1.2) and then returns `Ok(None)`, so `sync_repo_with_ahead_since`
  returns `SyncOutcome::Synced`. The daemon's apply phase maps `Synced` to
  `sync_success = true`, prints `🔁 synced <repo>`, resets `entry.failure_count = 0`, and
  removes the activity entry. Same for the clean-ahead path: `handle_ahead_push` swallows
  the failure and returns `Ok(())` → `NothingToDo` → also `sync_success = true`.
- **Evidence**: sync.rs:3060-3068 (`Ok(false) =>` and `Err(e) =>` arms only eprintln +
  `record_push_failure`, then flow continues to `run_release_pipeline_if_bumped` and
  `Ok(None)`); daemon.rs:3143-3150 (success arm).
- **Impact**: (a) The journal shows `🔁 synced` for a repo whose push just failed —
  false-healthy, the exact class fixed in v0.112.30 for the ahead-detection side.
  (b) `failure_count` never accumulates on push failure, so `MAX_FAILURES` (F1.6) never
  engages for the most common permanent-failure mode, and `ahead_since`-based backstop
  state is discarded with the activity entry each cycle. Push-failure visibility rests
  entirely on a disk ledger the daemon loop never reads (F1.2) and notifications that
  fire once ever (F1.1).
- **Suggested fix**: Introduce a distinct outcome (e.g. `SyncOutcome::PushFailed`) or have
  `push_background`'s false/Err propagate as `Err` from `stage_commit_and_push`/
  `handle_ahead_push` so the apply phase counts the failure and skips the "synced" log.
  Commit success + push failure should be `sync_success = false` for accounting purposes.

### F1.4 — [SEVERITY: HIGH] v0.112.29 bug class still live: `git ls-remote` (SSH) every 1s cycle for never-pushed / persistently-failing repos
- **Location**: daemon.rs:2766-2797 (ahead-override block) → daemon.rs:61-106
  (`count_unpushed_vs_configured_remotes`, `ls-remote` at line 88)
- **What**: When `status.ahead == 0 && (!has_upstream || upstream_ref_missing)` and
  `count_unpushed_vs_mirrors` returns 0, the daemon calls
  `count_unpushed_vs_configured_remotes`, which runs one `git ls-remote <remote>
  refs/heads/<branch>` (SSH round-trip) per configured remote — every cycle, with no
  cooldown. This state is *stable* for exactly the repos already in trouble: upstream
  configured by `configure_publish_upstream_if_missing` but tracking ref never created
  because every push fails (auth, missing forge repo, network). The block runs before the
  `MAX_FAILURES` gate, so even a repo the daemon has "abandoned" (F1.6) keeps issuing
  3 SSH connections/second forever.
- **Evidence**: daemon.rs:2774-2785 — the fallback chain
  `count_unpushed_vs_mirrors` → `count_unpushed_vs_configured_remotes` →
  `count_all_head_commits` runs on every pass through the loop; no entry in any cooldown
  map gates it (contrast the v0.112.30 `auto_create_cooldowns` fix at daemon.rs:2449-2452).
- **Impact**: Same defect v0.112.29 fixed for `push_mirror_remotes_create_only`, one
  code path over: permanent SSH churn (2-3 connections/sec/repo) for every repo whose
  push is broken, plus SSH-agent contention with legitimate pushes.
- **Suggested fix**: Cache the "tracking refs absent / remotes unreachable" verdict per
  repo with a 300s cooldown (mirror the `auto_create_cooldowns` pattern), or reorder so
  `count_all_head_commits` (purely local) is tried before any `ls-remote` — a missing
  tracking ref already implies every HEAD commit is unpushed, making the network call
  unnecessary in the `upstream_ref_missing` arm.

### F1.5 — [SEVERITY: HIGH] Directory-expansion bypasses the 100 MiB hard size limit and all per-file exclude patterns
- **Location**: sync.rs:665-905 (`stage_existing_files` recursion, expansion loop at
  ~734-815); filter gap at exclude.rs:1297-1304 (`should_stage_entry` returns `true` for
  any directory entry without per-file checks); reached from sync.rs:2878-2896
  (normal pipeline) and sync.rs:3197-3203 (bootstrap)
- **What**: Untracked fully-untracked subtrees arrive as a single DIRECTORY entry (libgit2
  collapses them). `should_stage_entry` approves the dir entry wholesale (size check only
  applies to `meta.is_file()`), then `stage_existing_files` recursively expands the dir and
  stages every file inside via `git add -A -- <paths>` — with NO re-application of
  `max_stage_file_bytes`, `exclude_file_patterns`, `auto_commit_exclude_patterns`, or
  `untracked_exclude_patterns` to the expanded files.
- **Evidence**: expansion loop pushes `rel.to_string_lossy()` for every non-symlink file
  whose ancestor dir names are not in `excluded_dir_names`; the only filters inside the
  loop are symlink/excluded-dir-name/`.git` checks. A 500 MiB `assets/video.mp4` inside a
  new `assets/` dir sails through; the same file at repo root would be rejected by
  `should_stage_entry`'s size arm.
- **Impact**: Violates the documented hard exclusion ("files larger than 100 MiB are NOT
  auto-staged", AGENTS.md). Giant blobs land in history → github 2 GiB pack guard trips
  (repo then silently skipped for github per `push_background`), codeberg quota burns, and
  the only remediation is history rewrite. Also a per-repo `auto_commit_exclude_patterns`
  escape hatch: patterns matching files but not their parent dir are ignored on first add.
- **Suggested fix**: After expansion (or during it), re-run the full per-file predicate
  (`should_stage_entry` on a synthetic `DiffFile` per expanded path, or at minimum the
  size check + `is_excluded_file` + `matches_untracked_exclude`) before appending to the
  stage list. Add a regression test with an oversized file nested in an untracked dir.

### F1.6 — [SEVERITY: HIGH] `MAX_FAILURES` permanently abandons repos after 5 failures — and `Blocked` (needs-human states) counts toward the budget
- **Location**: daemon.rs:2963-2979 (gate), 3096-3104 + 3186-3205 (`Blocked` →
  `sync_success = false` → `failure_count += 1`); sync.rs:310-333 (`check_conflict_state`
  returns `Blocked` for merge/rebase/cherry-pick in progress)
- **What**: Once `failure_count` hits 5 the loop logs "exceeded max failures, skipping
  until resolved" exactly once and then `continue`s on every subsequent cycle — forever.
  Nothing re-probes "resolved": the counter resets only on fingerprint change, successful
  sync, SIGHUP, or restart. A repo left with a merge in progress (a state that by
  definition requires the operator) returns `Blocked` each cycle, burns the budget in 5
  cycles, and is then silently dropped — precisely when the operator most needs the daemon
  to keep watching (e.g. to resume after they finish the merge). Note the per-cycle
  expensive work (status, diff entries, and the F1.4 SSH calls) still runs for skipped
  repos because the gate sits after those calls.
- **Evidence**: daemon.rs:2969-2978 — the skip branch contains no re-check, no cooldown
  expiry, no notification; the only reset paths are `entry.fingerprint != fingerprint`
  (failure_count = 0, line ~2946) and the success arms.
- **Impact**: Repo classes that hit transient-but-repeated errors (lock contention during
  operator rebase, a warden hook rejecting 5 commits, a merge left open overnight) fall
  off the sync radar permanently and silently until daemon restart. "Skipping until
  resolved" is unverifiable log fiction — nothing detects resolution.
- **Suggested fix**: Don't count `Blocked` toward `MAX_FAILURES` (it is not a transient
  failure); give the skip a timed cooldown (e.g. re-probe every 10-15 min) instead of an
  infinite one; and emit a notification (respecting the fixed F1.1 throttle) when the gate
  first engages.

### F1.7 — [SEVERITY: MEDIUM] `mirror_consecutive_fails` is write-never: the "Mirror Degraded" detection is dead code
- **Location**: daemon.rs:2198 (field), 2586/2915 (always `HashMap::new()`), 3322 (only read)
- **What**: The apply phase writes `entry.remote_failures = remote_failures` (line 3112)
  but nothing anywhere populates `mirror_consecutive_fails`. The sustained-state loop's
  third check (`*fail_count >= MIRROR_DEGRADED_THRESHOLD`) can therefore never fire.
- **Evidence**: `grep -n mirror_consecutive_fails src/` → 4 hits, no writes.
- **Impact**: A mirror that fails every push for a week produces no degraded-mirror signal
  (and per F1.1, even if it fired it would fire once). Either wire
  `entry.mirror_consecutive_fails = remote_failures.clone()` in the apply phase or delete
  the field and the dead check.

### F1.8 — [SEVERITY: MEDIUM] `stage_cooldowns` map is dead (never inserted) — and the filter-only path's "cooldown" comment relies on it
- **Location**: daemon.rs:2215 (declared), 2299 (SIGHUP clear), 2723 (only read);
  sync.rs:3525-3534 (`filter_only_cleared` → `NothingToDo` "so the daemon applies a
  cooldown")
- **What**: No `stage_cooldowns.insert` exists anywhere. The map is always empty, so the
  check at 2723 never fires, and it is also missing from the per-cycle `retain` block
  (daemon.rs:2294-2301 — the only cooldown map not pruned against `repo_set`). Meanwhile
  sync.rs's filter-only path documents that the daemon will apply a cooldown; in reality
  `NothingToDo` is treated as success, the activity entry is removed, and a repo whose
  dirty entries are all smudge/clean-filter noise is re-dispatched every
  `inactivity_push_delay_secs` forever (full status + diff + `git diff HEAD` each time).
- **Impact**: Wasted per-cycle work for filter-noisy repos (warden-managed repos with
  `filter=dracon` attributes are the common case) and a misleading cross-file contract.
- **Suggested fix**: Either insert a real cooldown when `filter_only_cleared` is observed
  (plumb a distinct outcome or have the daemon detect the repeat-NothingToDo pattern), or
  delete the map and fix the sync.rs comment.

### F1.9 — [SEVERITY: MEDIUM] Auto-create-on-discovery block charges every healthy repo `list_remotes` per cycle + `ls-remote` per remote every 5 min, forever
- **Location**: daemon.rs:2441-2484
- **What**: The v0.112.29/30 auto-create block sits BEFORE the `is_repo_ready` gate and
  has no readiness/health gate of its own: every repo with configured remotes pays a
  `git remote` subprocess every cycle (line 2443), and every 300s pays one
  `git ls-remote` (SSH) per configured remote inside `push_mirror_remotes_create_only`
  (`remote_repo_exists` per remote) — even for repos that have been fully synced for
  months. There is no "creation confirmed, stop checking" terminal state.
- **Impact**: With ~40 watched repos × 2-3 SSH remotes this is a permanent background hum
  of ~100 SSH connections per 5 minutes plus ~40 subprocesses/sec, existing solely to
  cover the first-boot window of brand-new repos.
- **Suggested fix**: Cache a per-repo "forge repos confirmed" verdict (persisted or at
  least session-long) once every remote answers `remote_repo_exists == true`; only re-enter
  the block for repos not yet confirmed.

### F1.10 — [SEVERITY: MEDIUM] `bootstrap_empty_repo_commit` (v0.112.30): no cooldown on `Ok(false)`, and no staged-hygiene sweep before the root commit
- **Location**: sync.rs:3112-3229; daemon.rs:2496-2523 (call site, `Ok(false) => {}`)
- **What**: Two gaps in the new bootstrap:
  1. All `Ok(false)` exits (nothing policy-compliant to stage, `auto_stage_untracked =
     false`, unowned, dry-run) get NO cooldown from the daemon (contrast the `Err` arm,
     which backs off 300s). A `git init`'d repo with no files yet — or with only excluded
     files — re-runs the whole bootstrap every 1s cycle: `load_repo_override` (disk+TOML),
     `detect_ownership` (multiple git subprocesses), `untracked_entries` (`git ls-files`).
     This is the same uncached-per-cycle class as F1.4/F1.9.
  2. The bootstrap stages its policy-filtered list but then commits **whatever is in the
     index** (`git diff --cached` is only checked for non-emptiness, sync.rs:3206-3211).
     Unlike the normal pipeline, it never runs the `clean_staged_paths` hygiene
     (`unstage_excluded_paths` / `unstage_oversized_paths`). An operator-staged 300 MiB
     file or a staged `.env`-adjacent path in a fresh repo is swept into the
     "auto: initial commit" unchecked.
- **Impact**: (1) permanent per-cycle subprocess churn for empty repos; (2) the size-limit
  and exclude policy can be defeated in the one commit the daemon makes on the operator's
  behalf in a brand-new repo.
- **Suggested fix**: Set a cooldown (60-300s) on `Ok(false)` as well; call
  `unstage_oversized_paths`/`unstage_excluded_paths` (or share `clean_staged_paths`)
  before the cached-diff check, and verify the staged set ⊆ the intended stage list.

### F1.11 — [SEVERITY: MEDIUM] Origin push failure short-circuits all mirror pushes for the cycle
- **Location**: sync.rs:1468-1490 (`push_background`: `return Ok(false)` on origin failure,
  before the `push_mirror_remotes` block)
- **What**: If the `origin` push fails (network blip to one forge, auth hiccup), the
  function returns immediately; github/gitlab/codeberg mirrors are never attempted that
  cycle. The 2026-07-09 audit (goal fb8ddd6b) established push-to-all as an invariant for
  the mirror path, but the origin arm still fails closed for the other forges.
- **Impact**: A repo whose `origin` is broken (e.g. points at a deleted GitHub repo)
  receives NO mirror pushes either — one forge's failure silently orphans the repo on all
  forges until origin is fixed. Compounds with F1.3 (the cycle is still reported "synced"
  on the next dirty cycle if the commit path is taken... actually here Ok(false) does
  record a failure via the caller, but mirrors remain unattempted).
- **Suggested fix**: Record the origin failure in `remote_failures`/the result accumulator
  and continue into the mirror block; return the aggregate.

### F1.12 — [SEVERITY: MEDIUM] `count_ahead_commits` hardcodes `origin/main..HEAD` — push-timeout scaling never engages for mirror-only or non-`main` repos
- **Location**: sync.rs:43-55; used at sync.rs:1402 (`push_background`)
- **What**: The timeout scaler measures ahead against `origin/main` only. For mirror-only
  repos (no `origin` — e.g. `.dracon`, or repos where origin was never added), and for
  repos still on `master` in the pre-rename window, the command fails → `Ok(0)` →
  `scale_push_timeout` always returns the base timeout.
- **Impact**: Exactly the repos the scaling was built for (large multi-commit pushes to
  mirrors — cf. the v0.112.10 >60s push in AGENTS.md) get the unscaled 60s timeout, burn
  `push_retries`, and fall into the failure path. The `⏫ scaling push timeout` log never
  fires for them.
- **Suggested fix**: Resolve the refspec dynamically: current branch name + the configured
  publish remote / first mirror tracking ref that exists (mirroring the
  `count_unpushed_vs_mirrors` fallback chain used in daemon.rs).

### F1.13 — [SEVERITY: MEDIUM] SIGHUP reload clears an inconsistent subset of daemon state
- **Location**: daemon.rs:2286-2304
- **What**: SIGHUP clears `activity`, `repair_cooldowns`, `filter_cooldowns`,
  `stage_cooldowns` — but NOT `empty_bootstrap_cooldowns`, `auto_create_cooldowns`,
  `remote_notify_cooldowns` (moot per F1.1), `pending_repos`, `in_flight`, and it does not
  reload `stuck_push_repos` from disk. Operator remediation flows that rely on SIGHUP
  ("fixed the repo config, now poke the daemon") work for ownership (activity cleared →
  ownership re-detected — this is today the ONLY way to refresh the cache-forever
  ownership verdict) but not for bootstrap/auto-create backoff or a stuck entry the
  operator just `unstuck`ed on disk via the CLI (`unstuck_repo` edits the disk file; the
  running daemon's in-memory map still holds the entry until its 5-min retry fires).
- **Suggested fix**: Clear all cooldown maps and re-run `load_stuck_push_repos()` in the
  SIGHUP arm; document that SIGHUP = full soft reset.

### F1.14 — [SEVERITY: MEDIUM] Trailing-drain timeout re-dispatches repos with live tasks: duplicate concurrent `sync_repo` inflates the failure ledger
- **Location**: daemon.rs:3153-3239 (trailing drain + forced `in_flight` clear at 3227-3238)
- **What**: On trailing-deadline expiry the daemon removes repos from `in_flight` while
  their tasks keep running (detached — the `FuturesUnordered` drop detaches them). The next
  cycle re-dispatches the same repo, so two `sync_repo` executions overlap: concurrent
  `git commit` (index.lock contention → one fails), concurrent pushes to the same remotes
  (the loser's non-FF/auth failure calls `record_push_failure`). The code comment calls
  this "recoverable", but the side effect lands in the stuck-push ledger: phantom
  `consecutive_failures` entries with misleading `last_error` ("another git process seems
  to be running"), which the report then surfaces as push-stuck HINTs. The still-running
  old task's eventual result is dropped — its `remote_failures` and any success signal
  (`record_push_success` does fire inside the task, at least) never reach the activity map.
- **Impact**: Self-inflicted failure accounting and doubled SSH load after any push slower
  than `trailing_drain_deadline_secs` (120s — large nested-submodule first pushes can
  exceed this per the 2026-07-09 notes).
- **Suggested fix**: Instead of clearing `in_flight` wholesale, keep a detached-task
  registry: on completion the task itself removes its repo from `in_flight` (via an
  `Arc<Mutex<HashSet>>` or a completion channel drained each cycle). Re-dispatch only when
  the registry shows the previous task finished.

### F1.15 — [SEVERITY: LOW] Per-cycle subprocess inventory and unthrottled log-spam paths in the daemon loop
- **Location**: daemon.rs:2433 (`configure_standard_remotes_if_missing` → up to 3
  `git remote get-url` when origin absent), 2443 (`git remote`), 2492 (`is_repo_ready` →
  `git rev-parse HEAD` every cycle even for healthy repos), 2531-2537
  (`configure_publish_upstream_if_missing` error eprintln every cycle on persistent
  failure), 2571 + 2454 (`load_repo_override` disk+TOML twice per repo per cycle),
  2692-2711 (`has_both_main_and_master` = 2 rev-parses + `has_only_master_branch` = 1-2
  more, every cycle; failure arms eprintln + `continue` every cycle); sync.rs:311-332
  (`check_conflict_state` warning every dispatch), sync.rs:424-440 (`auto_pull_merge` ℹ️
  lines every dispatch for no-origin/no-upstream repos)
- **What**: Roughly 6-8 subprocess spawns and 2 TOML parses per repo per 1s cycle before
  the fast-path `continue`, plus several `eprintln`-every-cycle paths on persistent
  failure states (rename-master failure, publish-upstream failure, conflict state).
- **Impact**: ~250 spawns/sec at 40 repos (measurable CPU/journal noise on the daemon
  host), and journal spam of identical lines until the underlying issue is fixed.
- **Suggested fix**: Cheap wins: short-circuit `is_repo_ready` for repos known-ready;
  cache `has_both_main_and_master`/`has_only_master_branch` verdicts per repo (branch-set
  changes are rare and could invalidate on fingerprint change); gate the recurring failure
  logs behind the (fixed, F1.1) notify-throttle map.

### F1.16 — [SEVERITY: LOW] `restore_excluded_paths` discards worktree edits for `auto_commit_exclude_patterns` matches, and is skipped on partial-failure paths (SUSPECTED)
- **Location**: sync.rs:1285-1330 (calls `restore_paths` → `git restore --staged
  --worktree -- <paths>`, git/staging.rs:294-343); call site sync.rs:3031 — AFTER commit
  and push; skipped when `svc.commit` fails (sync.rs:2967 `?`) and when `to_stage` is
  empty (sync.rs:3612-3616 early `Synced` return)
- **What**: `to_restore` entries are tracked Modified files that failed `should_stage_entry`
  — including operator-configured `auto_commit_exclude_patterns`. `git restore --staged
  --worktree` resets both index and worktree to HEAD, i.e. **deletes the operator's local
  edits** to those files after each successful commit. If the operator's intent for the
  exclude pattern is "keep these files, don't auto-commit them" (the AGENTS.md framing:
  short-lived ≠ very-wrong-to-commit, and exclusions are for commit-loop prevention), the
  daemon is instead enforcing "these files must always equal HEAD". SUSPECTED: this may be
  deliberate hygiene for tracked build artifacts (the same function family does
  `git rm --cached` on tracked excluded dirs), but the data-loss semantics for an
  operator-set exclude list are not documented anywhere I found. The skip-on-failure paths
  also make the behavior inconsistent: whether your excluded edits survive depends on
  whether an unrelated commit succeeded.
- **Impact**: Potential silent loss of uncommitted work in excluded paths; at minimum
  surprising.
- **Suggested fix**: Confirm intent with the operator. If exclusion ≠ reversion, drop
  `--worktree` (unstage-only) for `auto_commit_exclude_patterns` matches and keep the
  destructive arm only for hygiene-managed excluded dirs.

### F1.17 — [SEVERITY: LOW] Misc smaller defects
- **Batch limit applied per partition, not union**: sync.rs:2870-2882 takes `max_batch`
  from EACH of `regular_paths` and `gitlink_paths` (up to 2× `max_stage_batch_files` per
  commit); the comment claims the limit applies to the union.
- **Dead insert branch**: daemon.rs:2906-2922 — the `else` arm that inserts a fresh

## Summary (5 lines)

1. The daemon's failure-visibility stack is broken end-to-end: push failures report as
   "synced" (F1.3), the stuck ledger is split-brain with no enforced retry budget (F1.2),
   every throttled notification fires exactly once ever (F1.1), and the mirror-degraded
   detector is dead code (F1.7) — a repo can fail to push indefinitely with one log line.
2. The v0.112.29/30 hot-loop fixes are incomplete: SSH `ls-remote` still runs every 1s
   cycle per never-pushed repo (F1.4), healthy repos pay `ls-remote` every 5 min forever
   (F1.9), and bootstrap `Ok(false)` has no cooldown (F1.10).
3. Policy enforcement has real holes: the 100 MiB hard size limit is bypassed via untracked-
   directory expansion (F1.5) and the new root-commit bootstrap skips staged-hygiene (F1.10).
4. State-machine edges abandon repos silently: `MAX_FAILURES` is a permanent, notification-
   free skip that also counts needs-human `Blocked` states (F1.6), and the trailing-drain
   clear trades a stuck-set bug for duplicate concurrent syncs with phantom ledger failures (F1.14).
5. Highest-value fixes: route push failure into the apply phase as failure (F1.3), make the
   notify cooldowns actually expire (F1.1), and re-filter expanded directory files (F1.5) —
   each is small, local, and closes a whole failure class.

where verification required out-of-scope code or operator intent).

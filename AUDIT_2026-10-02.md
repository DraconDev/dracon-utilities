## Verified findings

### A1 — HIGH: Warden push scanning misses secrets in intermediate commits

Location: `dracon-warden/src/main.rs:5309–5324`, `5329`, `5351–5356`.

The pre-push hook uses `git diff remote_sha..local_sha`, which compares the
two endpoint trees. It does not scan each newly published commit. Introducing
a secret in one commit and deleting it in the next produces no changed file
at the endpoints. The empty scan list causes an immediate `continue`.
Both commits and the secret blob still become reachable on the destination.
Changing a secret back to its original value has the same underlying issue.

Reproduction used the exact hook constant extracted from current source,
executed directly in a disposable local Git repository; no push or external
service was used. The repository had three commits:

1. Base commit with a harmless text file.
2. Add `secret.txt` containing a synthetic quoted password assignment.
3. Delete `secret.txt`.

Feeding pre-push stdin with the base as the remote SHA and commit 2 as the
local SHA correctly rejected the secret (exit 1). Feeding the same base and
commit 3 returned exit 0. `git show <commit-2>:secret.txt` still returned the
synthetic assignment. This proves a history-level gap, not merely a regex
shape mismatch.

Impact requires plaintext to enter a local commit, for example after a filter
bypass. The hook advertises defense against that condition. Encryption at
the primary clean filter remains a separate protection.

Recommended correction: enumerate commits being published relative to the
destination, scan their introduced content including merge commits, and
preserve intentional plaintext exceptions. Regression coverage should include
add-then-delete and modify-then-revert across a single pushed range.

### A2 — MEDIUM: Interactive storage cleanup bypasses active-build protection

Location: `dracon-system/src/main.rs:7381–7386`;
`validate_storage_cleanup_path` at `7434`.

`storage --cleanup --apply` selects hotspots, checks Git tracking and protected
paths, and calls `remove_dir_all`. It never consults the active Rust build or
package-manager checks used by other cleanup commands. The cache-kind block
at `storage_hotspot_apply_is_blocked` covers only `cache`; `rust-build` and
`node-deps` remain deletable while in use.

Reproduction used the release binary built from this workspace and only
disposable files under `/tmp`. A temporary Git repository ignored `target/`,
which held one synthetic artifact. A live Python subprocess set its Linux
process name to `rustc` using `prctl` and stayed running with that repository
as its working directory. A temporary system policy set `protected_paths=[]`.

Command:

```sh
DRACON_SYSTEM_POLICY=<temporary-policy> target/release/dracon-system \
  storage <temporary-root> --cleanup --apply --min-size-mb 0 --kinds rust-build
```

Observed: process name `rustc`; cleanup exit 0; the process remained alive;
`target/` was deleted. The fixture models the existing detector's process
identity condition; it does not claim an actual compiler workload was run.

Impact: interrupting a build or dependency installation and removing generated
state in use. Existing default size thresholds do not prevent this on large
active projects.

Recommended correction: apply the same artifact activity checks to interactive
cleanup immediately before deletion, with fail-closed behavior on inspection
errors. Preserve package-cache coordination refusal. Cover both Rust targets
and dependency directories with temporary fixtures.

### A3 — MEDIUM: Spec verifier reports success when Cargo tests cannot run

Location: `scripts/verify-spec.sh:63–68`.

The script discards the exit status of `cargo test` and looks only for
`test result:.*FAILED` in its captured output. Compile errors, unavailable
dependencies, invalid manifests, and test-process crashes can exit nonzero
without producing that string. The script then prints `PASS: Core unit tests
pass`. CI invokes this script as the documented spec contract gate.

Reproduction ran the unchanged script in a temporary directory with three
placeholder utility repositories and controlled command stubs. The Cargo
stub returned 0 for `check`, but printed `error: could not compile fixture`
and returned 101 for `test`. Other unrelated checks were stubbed successful.
The verifier printed `PASS: Core unit tests pass`, `All invariants satisfied`,
and returned 0. This isolates the broken test-status decision.

Recommended correction: test Cargo's exit status directly, report its captured
output on failure, and use `--locked` consistently. Cover a compilation failure
and an ordinary failed test separately.

### A4 — HIGH: CI source pins and the parent lockfile cannot build together

`python3 scripts/check-nested-pins.py` passes: CI and Nix agree with each other
and workspace package versions match the current manifests.
`python3 scripts/check-nested-pins.py --check-local` fails on dracon-sync.
All three nested HEADs are newer than their configured pins:

| Utility | CI/Nix pin | Commits after pin at inspected HEAD |
|---|---|---:|
| sync | `b6e75318b25a548c713ebd6aef9f6cb9d5742d75` | 297 |
| system | `927832b28d1673fe2d900d8ea09b3a12bc5afc8a` | 339 |
| warden | `3aaa9029338877e561fd549b192dab1942f0c694` | 56 |

The checker without `--check-local` compares package versions against the
live nested manifests, not the pinned manifests. That allows a false pass
for the source combination actually checked out by CI. Pinned sync declares
`0.113.88`, pinned system declares `0.112.41`, and pinned warden declares
`0.113.14`; the parent lockfile instead records sync `0.113.92` and system
`0.112.42`.

Reproduction: copied current parent `Cargo.toml` and `Cargo.lock` into a
temporary directory, extracted each exact CI-pinned nested revision there
using `git archive`, and ran `cargo check --workspace --locked --offline`.
It exited 101: `cannot update the lock file ... because --locked was passed`.
No source, lockfile, or Git state in the canonical checkouts was altered.
This reproduces the checkout combination CI uses, rather than inferring
failure from revision differences alone. Nix evaluation succeeds but does
not establish that this source/lock combination can build.

Recommended correction: advance CI and Nix pins together with a lockfile
generated for those exact sources, and make the pin checker compare pinned
package metadata rather than only the live manifests. Local development
ahead of pins may remain allowed, but it must not silently replace validation
of the pinned build. No pin updates were made during this audit.

### A5 — HIGH: Quarantine overwrites a user file and follows its symlink

Location: `dracon-system/src/quarantine.rs:214`, `402`, `413`.

`quarantine_move` moves/copies the user's complete directory, then unconditionally
writes its metadata to `<entry>/.quarantine.json`. It neither reserves that name
nor rejects an existing file or symlink. A real user file with that name is
overwritten; a symlink causes `fs::write` to truncate its target outside the
quarantined directory. Restore subsequently removes the metadata pathname,
so it cannot recover the original file or symlink.

Reproduction used the current release binary with a temporary system policy,
an explicitly selected quarantine root under `/tmp`, and no live data. In one
case, the source contained `.quarantine.json` with synthetic user content. In
the second case it was a symlink to another synthetic file beside the source.
`quarantine move <source> --apply --json` and `quarantine restore <entry> --json`
both returned 0. In both cases the original marker was gone after restoration.
In the symlink case the outside file now contained quarantine metadata instead
of its original content. An ordinary file beside the marker was retained.

Impact: data loss during a command intended to provide recoverable staging;
an attacker-controlled directory can also redirect the metadata write to any
file writable by the operator. The usual protected-path check applies to the
source directory, not the target of this internal symlink.

Recommended correction: keep metadata outside the moved content in a private
entry envelope, or reject the reserved name before moving and use create-only,
no-follow publication. Preserve both regular-file and symlink cases in regression
coverage, including restore and cross-filesystem copy paths.

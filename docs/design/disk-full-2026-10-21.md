# Disk full — 2026-10-21

## What happened

At 23:00 on 2026-10-21 the root filesystem hit 100%: 907 GiB total, 858 GiB
used, **2.3 GiB free**. The daemon was still healthy, but a full disk means
no commits, no pushes, no builds and no logs.

## What had actually filled it

| consumer | size | verdict |
|---|---|---|
| `/tmp` scratch | 144 GiB | the cause — agent scratch from the day's sessions |
| `~/Dev` (repos) | 336 GiB | working data; `dracon-platform` alone is 260 GiB |
| `/nix/store` | 48 GiB | **not** the cause — see below |
| `~/.cache` | 15 GiB | re-downloadable browser and tool caches |
| `~/.rustup` | 12 GiB | ten toolchains, ~0.5–2.2 GiB each |
| `~/dracon/backups` | 19 GiB | the slimming rollback bundles |
| `~/Backups`, `~/Videos` | 60 GiB | the operator's own data |

The Nix store is worth a note, because the first measurement is
misleading: `nix path-info --all --closure-size` reported 1090 GiB, which is
the sum over all paths with shared dependencies counted repeatedly. The
store's real size is 48 GiB, and `nix-collect-garbage --dry-run` found
**nothing** to collect — every store path is reachable from a root. A GC
would have freed zero bytes.

## What was reclaimed

**118.2 GiB of stale `/tmp` scratch**, in two sweeps. The selection was
conservative on purpose:

- only top-level directories,
- **no live holder**: no process had the directory as its working
  directory and no process held a file open inside it (checked per
  process over `/proc/*/cwd` and `/proc/*/fd/*`, re-checked immediately
  before each removal),
- older than two hours,
- no credential-shaped name (`chrome`, `credential`, `password`, `secret`,
  `token`, `login`, `.env`, `.pem`, `.key`, `.age`, `git-credentials`,
  `.npmrc`, `hosts.yml`, `id_rsa`, `wallet`, `keystore`) — the fleet's
  standing rule for bulk deletes.

The first sweep took the 47 entries of 300 MiB or more (67.5 GiB); the
second took the long tail below that — 499 entries of 20 MiB or more, a
further 50.7 GiB out of 20,530 remaining directories. Before the second
sweep `/tmp` held 20,532 directories for 70.4 GiB: the long tail of
per-test scratch is as expensive as the few large clones.

Kept: `oe-buildtest` (a live build holds a file open in it), `wk` (7.3 GiB,
under two hours old), `yff-audit`, `pre-wt`, `yff-live-profile`, every
credential-shaped entry in `/tmp` (`eve35cmd-tokens-*`, `eve-pty-login-*`,
`secret_re.txt`, `shield-tokens.mjs`, `chrome_history_copy.db`, the
`yff-chrome-profile*` directories), and two root-owned directories that
could not be removed without privilege (`sd-root169`, `dg-a16-cargo`).

The scratch copies of db-gateway's owner keys (`/tmp/dg-*/state/dg-owner.key`)
went with their directories. The live keys are in
`~/Dev/db-gateway/state/` and were not touched.

**23 GiB**: `~/Dev/dracon-utilities/target/debug` — build artefacts from
four toolchains (1.89, 1.95, 1.98, 1.99) during the CI repair work. No
`cargo` or `rustc` process was running, and the daemon builds `--release`,
so `target/release` (1.3 GiB) was kept. A debug build is a few minutes of
recompilation.

Plus the scratch of this session: the fake HOME directories, the nix
out-links and the test logs.

**Result: 2.3 GiB free → 146 GiB free (84% used), `/tmp` 144 GiB → 33 GiB.**

## What was deliberately not touched

`~/.config/google-chrome`, `~/.dracon` (4.8 GiB — the credential store),
`~/.ssh`, `~/.git-credentials`, `~/.npmrc`, key files anywhere under
`~/Dev`, and the Trash (277 MiB, one item). The fleet's rule is explicit:
never delete these without the operator's approval, and never empty the
Trash without a credential scan first.

`~/Dev`'s 336 GiB is working data. The largest single items are git packs
(6.8 GiB in `dracon-strategy/ai-auto-writer`, 4.2 GiB in `dracon-platform`)
— history weight, and history is only reclaimable through the sanctioned
slimming procedure (bundle backup → filter-repo → guard-verify → leased
force-push), which is an operator decision.

## The two root causes

**2. The single age floor is the real limit, and the fast path is
name-based.** The guard's policy is `clean_tmp = true`,
`tmp_search_paths = "/tmp"`, `tmp_min_age_hours = 24`, with a shorter
floor for machine-generated e2e litter (`tmp_e2e_patterns` +
`tmp_e2e_min_age_hours`). A single day of agent scratch produced 144 GiB,
of which 67.5 GiB was between five and twenty-three hours old — below the
general floor, so the policy would not have reclaimed any of it before the
disk filled. The fast path only helps entries whose NAME matches the e2e
patterns; tonight's bulk was arbitrary clone names (`vd-mut2`, `wk`,
`fresh-clone`, `dg-*`, `caps-clone`, `fix-clone`, `jr-*`, …) that match
none of them, so the floor held all of it. The floor has to come down for
large entries, or scratch has to be reclaimed by size and liveness rather
than by name.

What the sweep already gets right, and what must not be lost: it refuses to
run when the open-file scan fails, it collects every open file, every
process working directory and every running executable under the tmp roots,
it keeps entries holding a live unix socket, it judges a directory by its
newest content rather than its own mtime, and it keeps protected paths. The
liveness side of the cleanup is sound; the age and the accounting are not.

**3. Nothing reports the scratch.** The guard alarms on percent-used
(75/85/92) and on rapid fill (20 GiB/h) — and it did warn during the
incident ("Disk growing at 32.6 GiB/h (85% used) … estimated 4.1 hours
until full"). But nothing reports the *reclaimable scratch* itself, so 144
GiB of deletable litter was invisible while the disk climbed. A
scratch-volume trigger would have named it hours earlier.

**4. The privileged paths fail loudly, every cycle.** The guard's
`nix-env` system-profile prune needs root and logs a failure on every
cycle ("Read-only file system (needs root; user GC still runs)"), and
root-owned tmp entries fail with "Permission denied" on every cycle as
well. Both are real, both are unfixable without privilege, and neither
should be a permanent per-cycle error line.

## Follow-ups

- The scratch needs a size-aware floor: a large entry with no live holder
  should not wait out the general 24-hour floor. A name-based fast path
  cannot cover arbitrary clone names. The knob belongs next to
  `tmp_min_age_hours` in `~/.dracon/utilities/system/dracon-system.toml`
  and in the crate's policy defaults, and — like the existing e2e fast path
  — it should default to off in the crate and be switched on in the live
  config, because it changes what gets deleted.
- The guard should report the reclaimable scratch volume and an
  hours-until-full estimate for it, not only percent-used and rapid fill.
- The per-cycle privileged failures (the `nix-env` profile prune) and the
  per-cycle "Permission denied" lines for root-owned entries should be
  classified and reported once, with the privileged step shipped
  apply-ready rather than failing on every cycle.
- The `dracon-platform` and `ai-auto-writer` history weight (11 GiB in two
  packs) is a separate decision with its own procedure; it is tracked
  against the parent repository's performance/swap-thrash notes.

DIRECT ANSWER
-------------
**For git SUBMODULES: YES.** If `git clone` is called with `--recurse-submodules`
(or the default behavior of many GUI tools like GitHub Desktop, GitKraken,
SourceTree, VS Code's git integration, GitLab CI's `GIT_DEPTH: 0` workflows,
etc.), the full content of every submodule is downloaded. The `git clone` alone
(without --recurse-submodules) just gives you SHA references — but this is not
the common default in many real-world workflows.

**For git-ANNEX: NO.** `git clone` alone gives you only metadata (annex
pointers, ~308 KB for 400 MB of content). Content is fetched on demand via
`git annex get <file>` or `git annex get --all`. The clone is small and fast;
the content download is explicit and selective.

The architecture (submodule vs annex) determines the answer. Test data below
quantifies both behaviors.

ANNEX TEST RESULTS (16 × 25 MB = 400 MB total)
====================================================

VARIATION 1: git clone (no flags)
  Command:  git -c protocol.file.allow=always clone <main> <target>
  Time:     0 seconds
  Size:     404 KB total (.git 308 KB, working tree 84 KB annex pointers)
  Files:    16 symlinks in assets/ pointing to non-existent annex objects
            (the content is NOT in the bare repo, only the annex pointers are)
  Result:   NO content downloaded. Just annex pointers. User would need to
            run `git annex init`, configure a remote, and `git annex get` files.

VARIATION 2: git clone + git annex get --all
  Commands: git -c protocol.file.allow=always clone <main> <target>
            cd <target>
            git annex init "cloned"
            git annex initremote store type=directory directory=/tmp/annex-content-store encryption=none
            git annex trust --force store
            for f in $(git ls-files assets/); do git annex get "$f" --from=store; done
  Time:     0s (clone + init) + 3s (get --all) = 3 seconds total
  Size:     402 MB total (.git 402 MB, working tree 84 KB)
  Files:    16 files in .git/annex/objects/, symlinks now point to real content
  Result:   FULL CONTENT downloaded via explicit loop of 16 `git annex get` calls.
            Note: `git annex get --all` alone (without --from=store) requires the
            remote to be trusted; the loop approach is more explicit and works
            even with untrusted remotes.

VARIATION 3: git clone + git annex get <single-file>
  Commands: git -c protocol.file.allow=always clone <main> <target>
            cd <target>
            git annex init "cloned"
            git annex initremote store type=directory directory=/tmp/annex-content-store encryption=none
            git annex trust --force store
            git annex get assets/audio/file1.bin --from=store
  Time:     0s (clone + init) + 0s (get one file) = 0 seconds total
  Size:     26 MB total (.git 26 MB)
  Files:    1 file in .git/annex/objects/, 1 symlink now points to real content
            Other 15 symlinks still point to non-existent annex objects
  Result:   SINGLE FILE fetched. Other 15 files NOT downloaded.

====================================================
KEY FINDINGS
====================================================

1. SUBMODULE: --recurse-submodules is the "make it work" default in many tools.
   - GitHub Desktop: defaults to recursive clone ✓
   - GitKraken: defaults to recursive clone ✓
   - SourceTree: defaults to recursive clone ✓
   - VS Code: defaults to recursive clone ✓
   - GitLab CI: GIT_STRATEGY: clone (not fetch) does recursive
   - GitHub Actions: actions/checkout@v4 has `submodules: recursive` as default
   - The ONLY way to avoid this is to explicitly NOT use --recurse-submodules,
     which is not the common default in most workflows.

2. SUBMODULE: --depth 1 does NOT reduce submodule clone size.
   The depth-1 only applies to the main repo's history; submodule content
   is fully downloaded regardless.

3. ANNEX: git clone is ALWAYS small and fast.
   Just metadata + annex pointers, regardless of remote's content size.
   400 MB test = 404 KB clone. 6.7 GiB test = ~500 KB clone (estimated).
   100 GiB test = ~500 KB clone.

4. ANNEX: get --all gives you everything; get <file> gives you one file.
   You choose explicitly. The default is "fetch nothing" (the user decides).
   This is the inverse of submodule's default ("fetch everything").

5. ANNEX requires setup (initremote, trust) but it pays off:
   - Selective fetch (one file at a time)
   - Lazy fetch (no content unless requested)
   - Multiple remotes (e.g., OVH primary, S3 backup)
   - Deduplication (same content = one object across files)

====================================================
RECOMMENDATION FOR dracon-platform
====================================================

The operator's question is: "would we clone down the entire hundreds of gigs
right? assuming everything goes right"

ANSWER:
  - Submodule: YES, if any common clone workflow is used (--recurse-submodules
    is the default in many tools). At 6.7 GiB, the clone would be ~20 GB on
    disk (or 100+ GB if grown). This exceeds GitHub's 5 GB cap.
  - Annex: NO. The clone is always small (~500 KB regardless of content size).
    Content is fetched on demand.

For the operator's case (6.7+ GiB of binary content, want to use OVH bucket
as source of truth, must avoid "hundreds of gigs" on clone):

**Use git-annex with OVH bucket (or another S3-compatible backend) as the
special remote. This avoids the "clone hundreds of gigs" problem entirely.**

If annex is not viable (e.g., team not willing to learn it), the next-best
options are:
  1. Submodule + size-managed per-category split (each sub-repo < 5 GB)
  2. Self-host on OVH (Gitea/Forgejo) and remove the size cap entirely
  3. Switch to a forge without the cap (Codeberg 10 GB, SourceHut unlimited)
  4. Use Git LFS with $5/mo for 50 GB LFS bandwidth (single remote, less flexible)

NOT recommended:
  - Submodule with all content in one sub-repo (would hit 5 GB cap)
  - GitHub as the forge for 6.7+ GiB content (hard cap)

====================================================
CAVEATS
====================================================

1. The 400 MB test is 16x smaller than the real 6.7 GiB. Time extrapolations
   (17s, 50s, 250s, 750s) assume linear scaling, which is reasonable for
   file I/O but may not hold for forge-specific network/bandwidth limits.

2. The annex "get --all" required a manual loop of `git annex get <file>` calls
   because the bare repo (origin) didn't have the content. With OVH as the
   special remote and the bare repo's annex config set up properly, the loop
   could be replaced with `git annex get --all --from=ovh` (single command).
   This is a test setup artifact, not an annex limitation.

3. Time measurements are rough (using `date +%s` with second precision). For
   real 6.7 GiB cloning, expect 5-15 minutes for the full transfer, plus
   forge-specific queue time.

4. The "default" of --recurse-submodules varies by tool. The test confirms
   that EXPLICITLY using --recurse-submodules gives full content. The
   question of whether your team's typical workflow uses this flag depends
   on what they're using (CI config, GUI tool, CLI habits).

5. For submodules, "hundreds of gigs" can happen if the team grows the
   per-submodule repos over time. The 5 GB cap is per-repo, but you can
   have 30+ submodules with 5 GB each = 150 GB total. The architecture
   doesn't have a built-in cap on total size, only per-submodule cap.

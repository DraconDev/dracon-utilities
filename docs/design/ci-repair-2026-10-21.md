# CI repair — 2026-10-21

## Why this document exists

The 2026-10-21 hardening session closed out the daemon's task-budget work
(`dracon-sync/docs/design/sync-operation-ownership-2026-10-21.md`). While
wiring that session's new task-budget parity suite into CI, the parent
repository's CI turned out to have been red for a very long time: **no
successful run in the last 120 runs**, the earliest of them already failing
on 2026-10-17. Every job except "Nix Flake" was failing.

Nothing about the session caused it. The three causes below are independent
of each other and predate it. This document records them, the fixes, and
what was verified locally versus what still needs a runner.

## Cause 1 — the nested pins rotted (Test, Release Build, MSRV, Scripts)

The parent workspace builds the three utilities as ordinary path members, so
cargo uses the LOCAL nested checkouts. CI checks out the PINNED revisions
instead. The parent's committed `Cargo.lock` carried the versions of the
local nested manifests, which the daemon had moved forward:

| crate | parent `Cargo.lock` | pinned manifest | pinned rev |
|---|---|---|---|
| dracon-sync | 0.113.95 | 0.113.95 | `2759b8c8` |
| dracon-system | 0.112.45 | 0.112.44 | `93b0edd9` |
| dracon-warden | 0.113.16 | 0.113.15 | `2388bee4` |

With the checkout and the lock file disagreeing, every `--locked` cargo step
failed:

```
error: cannot update the lock file /home/runner/work/.../Cargo.lock
because --locked was passed to prevent this
```

The same drift failed the spec contract's pin invariant
(`scripts/verify-spec.sh`, Invariant 3b → `scripts/check-nested-pins.py`).

**Why the pins rotted:** `flake.lock` had not been touched since 2026-10-19,
and nothing repins it on a schedule. The daily timer still named
`dracon-nested-pins-check` was repurposed to a git-identity guard on
2026-08-22, so the name still says "pins" while the job it runs
(`check-repo-identities.py`) has not checked pins since then.
`scripts/repin-nested-sources.py` is the sanctioned writer, but nothing
invokes it.

**Fix:** the three nested sources were repinned to their current GitHub
`main` — dracon-sync `bef3ce42`, dracon-system `7a39ac93`, dracon-warden
`84d0489b` — in `flake.lock` and in all seven `actions/checkout` refs per
utility in `ci.yml`. `scripts/check-nested-pins.py` now passes in both
modes, and the `crateVersion` fallbacks in `flake.nix` were kept in step by
the repin script itself.

### The repin script read the wrong forge

`remote_main()` picked "the first remote that is not called `origin`", which
is decided by `git remote`'s alphabetical listing and not by which forge the
CI checks out. For `dracon-system` that was `gitlab`, so a repin would have
pinned gitlab's `main`: a revision the CI checkout (github.com) may not have
at all, and one that lagged the commit the daemon had already published to
GitHub. Both consumers of the pin — the CI checkout and the `flake.lock`
input — fetch from the repository the CI names, so that repository now
decides which remote is authoritative:

- `remote_repo(url)` returns `(host, Owner/Repo)`. The host is part of the
  answer: GitHub and GitLab both host `DraconDev/<same-repo>`, so a
  path-only comparison cannot tell the forges apart.
- `ci_repository(workflow, fragment)` reads the `repository:` the CI
  checks out (a bare `Owner/Repo` means github.com).
- `ordered_remotes()` puts the remote holding that repository first, and is
  **fatal** when no local remote holds it — pinning a revision from another
  forge would break both consumers, so falling back to another remote is
  not a safe default.

`scripts/tests/test_repin_fallback.py` gained a `RemoteSelection` class
(13 tests total): URL spellings, the same path on two forges not comparing
equal, the CI repository being read from the workflow, the first remote
holding the CI's repository, and an absent repository being fatal.

## Cause 2 — the sources were not rustfmt-formatted (Lint)

`cargo fmt --all -- --check` failed on three spots in `dracon-system`
(`src/main.rs`, `src/tests.rs`). The daemon's auto-commits do not run
rustfmt, so formatting drift accumulates in the nested repositories and the
Lint job fails on it. `cargo fmt --all` fixed it; the change landed in the
nested repository as `7a39ac93` and is covered by the repin above.

## Cause 3 — the cargo-deny container could not resolve the toolchain (Dependencies)

The `cargo-deny-action` runs cargo-deny inside a container whose image ships
exactly one toolchain, `1.85.0-x86_64-unknown-linux-musl`. The repository's
`rust-toolchain.toml` says `channel = "stable"`, and rustup inside that
container resolves the file's channel against the container's musl host:

```
error: override toolchain 'stable-x86_64-unknown-linux-musl' is not
installed: the toolchain file at '/github/workspace/rust-toolchain.toml'
specifies an uninstalled toolchain
```

A second defect sat behind it: the job ran `cargo deny check` **on the
runner**, where the container's install never lands — that step could only
ever have failed with "cargo-deny: command not found", and the container's
own failure hid it.

**Fix:** the toolchain file is moved aside for the container run (it is only
a *default*; with it out of the way the container uses the toolchain its own
image ships) and restored immediately after, including on failure. The deny
check now runs where cargo-deny actually is — inside the action's container,
which is also the only place `deny.toml`'s `[sources] unknown-git` /
`unknown-registry` policy can be enforced (audit F83, 2026-09-27).

## Cause 4 — the test suite was never hermetic (Test, Minimum Toolchain, Nix Flake)

With the pipeline running again, the test job failed for reasons that had
been hidden behind the lock-file error for two months. The suite had never
run on a runner, and it depended on the developer's machine:

- **No global Git identity.** Dozens of tests create a temporary repository
  and commit in it. A commit needs an author, and the author came from the
  operator's `~/.gitconfig`. A runner has none, so every one of those
  commits failed ("push to mirror failed" — the commit never happened).
- **No `init.defaultBranch`.** The operator's config sets `main`; a runner
  defaults to `master`, so a bare fixture repository's HEAD pointed at the
  branch the test then deleted, and the remote refused ("deleting the
  current branch is denied").
- **No age identity.** The warden tests encrypted with an identity loaded
  from the operator's key search path. With none, the encryption had no
  recipient ("No master identity or public recipients found for
  encryption").
- **The warden's own filter corrupted one of its tests.** The test
  `foreign_marker_does_not_suppress_the_scan` needs a secret-shaped token
  literal. The warden's clean filter encrypts such a literal in source, so
  committing the test rewrote its body into a `[DRACON_SECRET:...]` tag —
  1016 bytes where the test asserts 40, and the committed source failed its
  own assertion. The token is now assembled at run time, so the source
  holds no matchable literal and the filter leaves the file alone
  (verified: `git hash-object` with and without the filter are identical).

The fix is a Git configuration for the test environment, in the shape a
developer's machine already has — a **global config file**, not environment
variables. An environment variable (`GIT_AUTHOR_NAME`) outranks both a
local `git config user.name` and a `-c user.name=…` override, so several
tests that deliberately commit under a simulated identity (the warden's
poisoned-author push test, the mailmap test, the ownership test) would
commit as the injected identity instead of the one they set up. A global
file has the right precedence: a test's own local config or `-c` override
still wins, and a fresh temporary repository still finds an author.

- The CI Test and Minimum Toolchain jobs install it in a step.
- The Nix build has no home at all, so the flake writes the same file into
  the sandbox (`preBuild`) and points `GIT_CONFIG_GLOBAL` at it.

The warden tests were made hermetic on their own side: each one now uses an
in-memory age identity instead of whatever the machine has, and the
round-trip tests use ONE security object, so the body is encrypted and
decrypted with the same key. Previously each call built a new object with a
newly generated identity, and the round trip only passed where a stable
identity happened to be loaded from the key search path.

## Cause 5 — clippy on the runner's newer toolchain (Lint, Minimum Toolchain)

The runner's stable is rustc 1.99.1; the machine's was 1.97.1. Three lints
that only the newer clippy reports failed the build:

- `clippy::chunks_exact_to_as_chunks` (new in 1.99) at
  `dracon-sync/src/storage_core/journal.rs` and `…/staging.rs`: a constant
  chunk size now has to be `as_chunks::<2>()`.
- `clippy::items_after_test_module` in `dracon-system/src/managed_oom.rs`:
  `recover_loop` sat after the test module.
- `clippy::unnecessary_min_or_max` in `dracon-system/src/cpu_limit.rs`.

The Minimum Toolchain job (1.89.0, `--all-targets`) reported two more that
the newer clippy no longer does: `clippy::nonminimal_bool`
(`!x.is_ok()` → `x.is_err()`) in `dracon-system/src/managed_oom.rs`. All
five are fixed at source, and both toolchains are clean with
`--all-targets`.

## Cause 6 — the newly pinned scripts did not lint (Scripts)

The repin brought two months of new scripts into the shellcheck gate, and
fifteen findings failed it: `mkdir -p -m 700` (the mode only applies to
the deepest directory), unquoted `[[ … == $var ]]` right-hand sides, a `cd`
without `|| exit`, `ls | wc -l`, `cat | tee`, `A && B || C` chains, an
unused loop variable, a `status` referenced before assignment, and a nix
expression in single quotes that shellcheck reads as a non-expanding
string. All are fixed in the three repositories the findings live in.

## Cause 7 — the daemon pointed ssh at a file that may not exist (Test)

`git_ssh_hardening()` always passed `-F $HOME/.dracon/secrets/ssh/config`.
When that file is absent, ssh refuses to start ("Can't open user config
file ..."), so every SSH push on a machine without the fleet's config store
failed with a configuration error instead of the real cause — and the
daemon's error reporting carried the wrong thing. The flag is now wired in
only when the file exists; the rest of the hardening is unchanged.

## Cause 8 — the warden's own filter poisoned a second test (Test, Nix Flake)

The S3 storage tests carried the same defect as the scan test, in a second
file: the AWS access key in the fixture is secret-shaped, so the warden's
clean filter encrypted it in the committed blob. The working tree (which
the filter decrypts on checkout) had the key, so the test passed locally;
on the runner and in the Nix sandbox the committed source carried a
`[DRACON_SECRET:...]` tag, the credential's length and charset checks
rejected it, and twelve tests failed. The key is now assembled at run time
— verified the same way: `git hash-object` with and without the filter are
identical, so the filter leaves the file alone.

## Cause 9 — tests that depend on the checkout, the runtime or the terminal (Test, Nix Flake)

Three more environment dependencies, each with a different shape:

- **A detached HEAD has no branch to measure.** The GitHub pack-size
  measurement reads the current branch, and `actions/checkout` checks a
  SHA out as a detached HEAD, so the size was unmeasurable and the
  measurement test failed. The test now uses a fixture repository instead
  of whatever checkout it happens to run in.
- **The Node runner.** The bucket-runner qualification fixture and the
  runner bridge spawn `node <bundle>`; the Nix sandbox has no Node in its
  build inputs, so the spawn failed with a "No such file or directory"
  that named the bundle rather than the missing runtime. The tests that
  need a runtime now check for it and report the skip. The CI jobs, which
  do have Node, install the bucket-runner's declared and locked
  dependencies (`npm ci`) before the suite runs.
- **Colour codes in the rendered table.** comfy-table styles the table
  with ANSI colours when stdout is a terminal, and the Nix build's stdout
  is styled while a piped test run is not. The width assertion measured
  the escape sequences as columns, so the same table measured 453 columns
  in the sandbox and 165 in a pipe. The width is now measured on the text
  with the escapes stripped — the escapes occupy no columns on screen.

## Also wired: the task-budget parity suite

The task-budget parity check and its regression suite live in the nested
`dracon-sync` repository, and a checker whose suite never runs is worthless
(the same lesson as audit M9, which wired the unit-deployment suites). The
parent CI now runs the suite. It is skipped, with a visible `::warning::`,
while the pinned nested checkout predates the suite; the repin above
brought the pin past the commit that carries it, so the suite now runs.

## Follow-ups (not done here)

- **Nothing repins the pins.** The daily timer that looks like the pin
  checker runs an identity guard instead. Until that is reconciled, the
  pins will drift again as the daemon commits — and the drift is silent:
  the failure only shows up as a red CI. A repin on a schedule (or a CI
  step that repins and verifies) is the durable fix.
- **The test suite still depends on the machine for the Git identity.**
  The CI jobs and the Nix build now install the same global Git
  configuration a developer's machine has, but a bare `cargo test` on a
  fresh machine still fails the tests that commit in temporary
  repositories. The durable fix is a fixture that sets a local identity in
  every repository it creates.
- The `hellhunter` identity drift the daily identity guard reports
  (`'-' <'-'>`) is a separate, pre-existing finding and was not touched.

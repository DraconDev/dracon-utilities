  Three things worth knowing before deciding:

  1. Per-path encryption already works. The exempt list is deliberately emitted
     before protected-pattern lines in the managed .gitattributes, so an
     explicitly protected path wins on git's last-match-wins rule. You can
     already add something like internal-dashboards/** to protected_patterns and
     those PNGs get whole-file encrypted. What's missing is only shipped
     defaults for known agent screenshot dirs, the way we did for transcripts.

  2. Blanket *.png encryption would be hostile. Game repos commit artwork and
     screenshots as deliverables — encrypted blobs break GitHub rendering,
     diffs, README hotlinks, and force every viewer through age keys. Note some
     dump dirs (.pi/chrome-screenshots/, audit-*/screenshots/) are already

     refuses image/video files going to public remotes (Warden already does
     visibility-aware checks elsewhere) would fail closed on exactly the news

  cost is not the problem.

  Crypto and size: cheap. age (X25519 + ChaCha20) streams at GB/s, so a
  screenshot encrypts in milliseconds — you'd never feel it. Size-wise, Warden's
  whole-file format is a base64-wrapped age payload, so roughly +33% per file (a
  2 MB PNG becomes ~2.7 MB). Worth knowing at deathrun scale, but not a
  dealbreaker. Encrypted bytes also don't delta-compress — but neither do PNGs
  or MP4s, so nothing lost there.

  The real cost is functional: an encrypted image stops being an image to anyone
  without keys. No GitHub rendering or thumbnails, no README embeds, no PR
  previews, no visual diffs, no hotlinking. Every viewer needs an age identity
  plus a working Warden smudge setup — collaborators, CI screenshot-diffing,
  future-you after a key loss. And an encrypted merge conflict is unresolvable
  by hand. For your game repos, where screenshots are deliverables and
  marketing, blanket encryption would destroy the value of committing them.

  So my actual position: encrypting is the right tool for sensitive images
  (internal dashboards, customer data on screen, credentials visible in a shot)
  and the wrong default for ordinary ones. Two honest caveats even then:

  • Encryption mitigates exposure but doesn't prevent the "oops, it's public"
    event — the file still lands in the public repo, just as ciphertext. A
    push-time block is what stops the event itself.
  • Ciphertext-public-is-fine holds only if recipient hygiene is good. If the
    repo's recipient set is broad or sloppy, the encryption is theater.

  That's why I'd scope it: default-protect the known agent screenshot dump
  paths, leave game art alone, and consider the public-push guard as the
  backstop.

◆ The rule has to be enforceable by what Warden can actually see — and Warden
  sees paths, not pixels. It can't OCR a screenshot, so any rule must reduce to
  path patterns + repo visibility + explicit overrides. With that constraint,
  here's the rule I'd propose, mirroring the commit policy's "very wrong"
  framing:

  Three buckets for any binary:

  1. Must be committed and safe visible → plain. Game art, marketing
     screenshots, docs diagrams, test fixtures. Encryption here is pure loss (no
     rendering, no diff).
  2. Must be committed but unsafe visible → encrypted. This is the new bucket:
     agent captures of internal systems, customer data on screen, credentials in
     a shot, unreleased NDA material, audit evidence that must persist.
  3. Must not be committed → ignored or blocked. Regeneratable dumps (already
     hygiene-ignored), credential files, ephemeral captures.

  Decision procedure for landing in bucket 2 — all three must hold:

  • Producer or location signal. The file sits under a known agent-capture path
    (the screenshot equivalent of our conversation-dump list) or a
    sensitive-area pattern — never a bare *.png. Same scoping discipline as the
    transcript patterns: specific enough to never catch screenshot-service.rs or
    a game's screenshots/ deliverable folder.
  • Visibility test. Public repo, or content sensitive regardless of visibility
    (customer data, creds). Private repo + non-sensitive content stays in bucket
    1.
  • No explicit override. Per-repo protected_patterns can add paths (explicit
    already wins over the binary exemption today), and carve-outs require a
    documented reason, following the existing override culture.

  The honest limitation to state up front: the rule is only as good as path
  discipline. If an agent writes an internal dashboard capture to
  assets/cool-pic.png, no pattern catches it. So part of the rule has to be
  producer-side — agent loops configured to write captures under agreed
  directories — with the public-push guard as the backstop for everything that
  slips through.

◆ Three things, in priority order — and one thing I wouldn't do.

  1. A one-shot audit of what's already committed. The new option only protects
  future commits. A quick pass over images already sitting in public repos
  answers the actual question — "are we already exposed?" — and it's cheap. If
  it comes back clean (likely, given your content is mostly game art and test
  frames), you're done worrying.

  2. Producer path discipline for agent loops. The option only catches what
  lands under its patterns. If the live-browser-audit loop writes captures
  wherever it pleases, the pattern has gaps. This isn't code — it's agreeing on
  capture directories per loop and pointing the option at them. Without it, the
  knob is loaded but unloaded... sorry, armed but blind.

  3. The public-push guard, if the audit says it's warranted. Refusing (or
  loudly warning on) binary media pushed to public remotes is the real backstop
  for everything patterns miss. It's the most complex of the three, so I'd only
  build it if the audit turns up genuine near-misses rather than clean results.

  What I wouldn't do: blanket-encrypt defaults, or anything cleverer like
  screenshot content scanning/OCR. The former breaks your art workflows for a
  threat you haven't observed; the latter is a research project disguised as a
  feature.

  My honest take: run the audit, and if it's clean, stop there. The option
  exists for the day someone needs it — which was the whole point.
